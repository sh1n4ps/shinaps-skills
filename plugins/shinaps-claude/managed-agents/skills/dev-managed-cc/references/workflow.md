# dev の工程（Managed Agents）

Claude Code の dev の工程を、Managed Agents のセッション向けに絞ったもの。Claude Code でメインが行う作業は lead が行う。役割・人数は初回メッセージの体制（[実装体制の判断](staffing.md)）の担当で進め（BASIC・ULTRAでは必須担当を下限に追加できる）、担当の委任・継続・作業先・出力は[起動手順](launch.md)に従う。

## 役割と継続

下の表は各役割の工程と継続を定める。起動する担当と人数は、受け取った体制の表（`staffing.md`）に従う。

| 工程 | 役割定義 | 継続と責任 |
| --- | --- | --- |
| Phase 3 | `shinaps-architect` | 独立設計担当を置く場合（ULTRAでは必須、BASICでは追加できる）。独立案と、その案への追加の質問への回答だけを担う |
| Phase 4 | `shinaps-plan-reviewer` | 計画レビューと計画の簡素化をあわせて見る。修正版の再確認も同じ担当 |
| Phase 6 | `shinaps-reviewer` | 独立コードレビューを含む担当はレビューラウンドごとに新規。規約照合と可読性・慣習レビューを技術領域ごとに置く担当は、ラウンドと修正サイクルをまたいで継続し、技術領域が増えたら追加 |

- 目的・範囲・規約全文・必読ファイル・今回の役割・担当番号・確認対象の版・依頼するレビューの種類を依頼に渡す（独立設計担当への依頼はPhase 3に従う）。
- 計画の確認と実装後の確認に、[レビューの共通契約](review.md)の「対象の固定」「独立性」「完了の判定」を適用する。計画の確認では対象の版を計画の内容のハッシュとし、差分・機械検査・変更範囲の文は適用しない。Phase 4 の入力として定めた両案は他担当の結果に当たらない。独立案（Phase 3）はPhase 3の節に従う。
- 各担当の報告は全文を作業記録の `raw/` に保存し、対象版・役割・担当番号・確認範囲・完了状態を対応づける。Phase 4 の採否は `plan.md`、Phase 6 の採否は `fix-log.md` の「指摘の採否」の節に書く。
- lead は、体制と工程の調整、調査・設計・計画の統合・実装・検証・修正、指摘の検証と採否、修正計画、担当の委任・待機、結果と未解決事項の取りまとめ、利用者判断の取り次ぎ、作業先・書き込み制限の比較・git・draft PR を行う。体制が求める独立確認を lead の自己確認で代えない。継続のターンで来る質問・修正も同じように扱う。
- **修正サイクル**: 継続のターンで実装の修正が必要になったら、契機によらず、未対応の指摘の集合を一つの入力にして次の順に進める。
  1. lead が修正計画と、影響を受ける工程を決める。
  2. 設計・契約・検証条件を変える場合だけ、Phase 4 の扱いで再確認する。
  3. lead が修正する（Phase 5）。
  4. Phase 6 の担当（受け取った体制のとおり）が確認する。範囲は修正とその影響範囲とし、確定できなければ広げる。
  5. Phase 7 で統合・修正する。

## Phase 1: タスクと体制

初回メッセージの必須入力が揃っていることを確かめ、目的・受入条件・範囲を確定する。作業先を[起動手順](launch.md)に従って用意し、関連コードと検証方法を必要な範囲だけ確認して、初回メッセージの体制の担当で進め、BASIC・ULTRAでは追加の担当を決め、作業記録に残す。

## Phase 2: 規約と必要な探索

規約の範囲は [SKILL.md の規約](../SKILL.md#規約)に従う。lead が読んで以降の担当へ全文を渡す。探索は lead と独立設計担当が、それぞれ自分の設計に必要な範囲で行う。

## Phase 3: 設計と計画

lead は設計を始める前に[設計の観点](design.md)を読み、その観点と書式で計画を作る。LITEでは短い計画と検証方針にする。

独立設計担当を置く場合は、次の性質を保つ。

- 独立設計担当への依頼（追加の質問を含む）には、要件・制約・規約全文・引き継いだ成果物だけを入れ、lead の案・結論・探索の結果は入れない。
- lead は独立案を読む前に自案を作業記録の `raw/design-main.md` に保存し、保存後は変えない（例: 自案を保存してから独立設計担当へ委任する）。
- lead が両案を根拠とトレードオフで比べて一つの計画にまとめ、`plan.md` に書く。比較の節には論点ごとの採否と理由を書く。

## Phase 4: 計画の確認

計画レビュー担当へ同じ計画を渡し、計画レビューと計画の簡素化をあわせて依頼し、指摘を「指摘の検証と統合」に従って扱う。独立設計担当を置いた場合は、統合計画・両案・比較の節を渡し、独立案の論点を根拠なく退けていないかも確かめさせる。LITEではこの工程を起動せず、計画はPhase 6の独立コードレビューの担当が、計画自体も誤りうる前提で確かめる。同じ対象について初回を1として最大2ラウンドとする。上限到達後に計画を修正した場合は、未再確認の変更と残課題を記録する。重大な設計リスク、仕様・許可の未決事項、必要な担当の未完了があれば Phase 5 へ進まず未完了で返す。

## Phase 5: 実装と検証

lead が確定計画を実装する。

- 実装前に、規約と、計画に記した同種の既存実装2つを確認する（計画に無ければ選んで記す）。対象ファイルの現在の内容を読んでから編集する。
- 計画で決めた最終構造を実装する。必要な移動・分割を差分削減のために省略せず、全利用側の参照更新・旧経路や重複の解消・既存利用側の回帰確認まで行う。目的・仕様・受入条件の変更が必要と分かったら、該当作業を止めて `状態: 質問` で利用者に確認する。
- 検証やレビューの指摘には原因を確認して対処する。期待値や受入条件を弱めて成功扱いにしない。
- 実装後、目的を保ったまま削除・統合できる処理を確かめ、不要な分岐・重複・互換層を減らしてからセルフレビューする。
- lead の定義のテスト方針に沿って、プロジェクトの規約・CI・変更の影響に応じた必須検証を行う。実装ミスによる検証失敗の自己修正は3回まで。超えたら根拠と未解決点を記録して未完了で返す。

## Phase 6: 実装後の確認

[レビューの共通契約](review.md)に従い、同じ差分を固定して、受け取った体制の担当と追加した担当を並行して委任する。設計適合性は、独立コードレビューの種類の中で毎回依頼する。変更範囲の確認コマンドは比較元からの差分（`git diff <比較元> -- <path>`）を渡す。規約は [SKILL.md の規約](../SKILL.md#規約) の範囲で、機械検査は実行しない。

## 指摘の検証と統合（Phase 4・6）

[レビューの共通契約](review.md)の「指摘の検証と統合」に従う。利用者への確認は `状態: 質問` で行う。

## Phase 7〜8: 修正と終了判定

lead が採否に従って修正する。実装後の全体レビューは、最初の dev と各修正サイクルのそれぞれで、初回を1として最大2ラウンド。同じサイクルの中の増員・交代・計画変更では上限をリセットしない。2回目の後に修正したら必要なテストを行い、最終差分が再レビューされていないことを報告する。重大な未解決事項、必須検証の失敗、必要な担当の未完了が残れば品質上の完了とは報告しない。

## Phase 9: コミット・push・draft PR と報告

1. コミット単位を依存順に確定する。stage は合意した範囲のパスだけにし、作業記録やその他のファイルを含めない。
2. 許可された場合だけ commit する。
3. 許可された場合だけ head ブランチへ push する。
4. 許可された場合だけ draft PR を作る。
5. [起動手順](launch.md)の出力を置き、状態行と SKILL.md の最終報告を書く。

許可されていない操作はその手前で止め、行わなかった操作を最終報告に書く。
