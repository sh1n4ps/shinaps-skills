# dev の工程（Managed Agents）

Claude Code の dev の工程を、Managed Agents のセッション向けに絞ったもの。役割・人数は[実装体制の判断](staffing.md)に従って作業ごとに決め、担当の委任・継続・作業先・出力は[起動手順](launch.md)に従う。

## 役割と継続

下の表は必須起動一覧ではない。

| 工程 | 役割定義 | 継続と責任 |
| --- | --- | --- |
| Phase 3・4・6・7 | `shinaps-architect` | 担当1は設計・統合・設計適合性を継続。担当2以降は独立設計と追加確認のみ |
| Phase 4 | `shinaps-plan-reviewer` | 修正版の再確認も同じ担当 |
| Phase 4・6 | `shinaps-simplifier` | 計画の再確認は継続。実装の簡素化は別担当 |
| Phase 5・7 | `shinaps-implementer` | 1体。同じ担当へ修正を返す |
| Phase 6 | `shinaps-reviewer` | 実装担当とは別。レビューラウンドごとに新規。規約照合も担う |

- 目的・範囲・規約全文・必読ファイル・今回の役割・担当番号・確認対象の版を依頼に渡す。実装担当にはファイルの所有範囲を明記する。
- 独立確認する担当には同じ版の入力を渡し、今回の他担当の結果を読ませない。対象を編集中にレビューせず、全結果が揃うまで lead と実装担当も対象を変えない。
- 起動失敗・空回答・未確認範囲を「指摘なし」にしない。

## Phase 1: タスクと初期体制

初回メッセージの必須入力が揃っていることを確かめ、目的・受入条件・範囲を確定する。作業先を[起動手順](launch.md)に従って用意し、関連コードと検証方法を必要な範囲だけ確認して初期体制を決め、作業記録に残す。

## Phase 2: 規約と必要な探索

規約の範囲は [SKILL.md の規約](../SKILL.md#規約)に従う。lead が読んで以降の担当へ全文を渡す。lead（設計担当がいれば設計担当も）が関連ファイルを確認し、実装担当は実装の詳細を調べる。探索の専任は委任しない。

## Phase 3: 設計と計画

設計責任者は設計担当1、専任なしなら lead とする。計画には目的・不変条件・変更範囲（対象ファイルと責務）・実装順・検証を書く。設計担当が複数なら同じ入力で独立に検討させ、担当1が根拠で一つの案へ統合する。

## Phase 4: 計画の確認

選んだ計画レビュー・計画簡素化の担当へ同じ計画を渡し、指摘を「指摘の検証と統合」に従って扱う。同じ対象について初回を1として最大2ラウンドとする。上限到達後に計画を修正した場合は、未再確認の変更と残課題を記録する。重大な設計リスク、仕様・許可の未決事項、必要な担当の未完了があれば Phase 5 へ進まず未完了で返す。

## Phase 5: 実装と検証

実装担当1体へ確定計画・必読ファイル・規約全文・所有ファイル・必要な検証を渡す。実装担当は計画を実装し、簡素化・セルフレビュー・必須検証を行う。実装ミスによる検証失敗の自己修正は3回まで。lead は報告だけで完了とせず、差分と検証の根拠を確認する。

## Phase 6: 実装後の確認

同じ差分を固定し、選んだ担当を並行して委任する。実装者と独立したコードレビューは最低1体。設計適合性は設計担当1（専任なしなら lead）、規約照合はコードレビュー担当、実装の簡素化は選んだ simplifier（専任なしなら実装担当とコードレビュー担当）が確認する。staged・unstaged・untracked を含めて対象を特定する。

## 指摘の検証と統合（Phase 4・6）

設計責任者（設計担当1、専任なしなら lead）が全指摘の根拠・誤認・重複・対立・未確認を区別し、全項目の採否と理由、必要な修正と検証をまとめる。再現・検証が必要なら実装担当へ依頼する。仕様・受入条件の変更や許可範囲の拡大は利用者の合意前に採用しない。

## Phase 7〜8: 修正と終了判定

修正指示を同じ実装担当へ返す。実装後の全体レビューは初回を1として最大2ラウンド。2回目の後に修正したら必要なテストを行い、最終差分が再レビューされていないことを報告する。重大な未解決事項、必須検証の失敗、必要な担当の未完了が残れば品質上の完了とは報告しない。

## Phase 9: コミット・push・draft PR と報告

1. コミット単位を依存順に確定する。stage は合意した範囲のパスだけにし、作業記録やその他のファイルを含めない。
2. 許可された場合だけ commit する。
3. 許可された場合だけ head ブランチへ push する。
4. 許可された場合だけ draft PR を作る。
5. [起動手順](launch.md)の出力を置き、状態行と SKILL.md の最終報告を書く。

許可されていない操作はその手前で止め、行わなかった操作を最終報告に書く。
