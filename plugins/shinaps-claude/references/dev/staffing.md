# 実装体制の判断

devの体制はLITE・BASIC・ULTRAの3段階で、作業ごとに人が選ぶ。BASIC・ULTRAでは選んだ体制の必須担当を下限にメインが担当を追加でき、LITEは表の2名だけで進める。「メイン」はdevを実行するClaude Codeのセッション（CLIまたは対話）を指し、linear-executeの進行役とは区別する。linear-execute の進行役は各Issue開始時に、確認した体制と、受入条件・関連範囲・既存検証・リスクを材料として渡す。

## 体制の種類

| 役割 | LITE | BASIC | ULTRA |
| --- | --- | --- | --- |
| 設計 | 置かない（実装担当が短い計画と検証方針を作る） | 1名（設計担当1） | 2名（独立に設計し、担当1が統合） |
| 計画レビュー | 置かない | 1名 | 2名 |
| 計画簡素化 | 置かない | 1名 | 2名 |
| 実装 | 1名 | 1名 | 1名 |
| 実装後の設計適合性 | 独立レビュー担当（design 観点で計画と実コードを照合する） | 設計担当1 | 設計担当1 |
| 実装後の独立コードレビュー | 独立したOpusの1名（正しさ・可読性・慣習・規約照合・簡素化を兼ねる） | 独立した1名（可読性・慣習と規約照合も兼ねる） | 1名 |
| 実装後の refine | （独立レビュー担当が兼ねる） | （独立コードレビューの担当が兼ねる） | 1名 |
| 実装後の可読性・慣習 | （独立レビュー担当が兼ねる） | （独立コードレビューの担当が兼ねる） | 技術領域ごとに1名 |
| 実装後の簡素化 | （独立レビュー担当が兼ねる） | 独立した1名 | 1名 |
| 指摘の整理 | 実装担当（設計責任者） | 設計担当1（計画と実装後） | 計画と実装後の各検証ラウンドで、新規の指摘検証担当1名 |
| 採否 | 実装担当（設計責任者） | 設計担当1 | 設計担当1 |

設計責任者は設計担当1、設計担当を置かない体制（LITE）では実装担当とする。各役割の定義・継続・新規にする単位は[工程](workflow.md)の「役割と継続」に従う。探索は必須にしない。探索担当を置かない場合は、設計担当（LITEでは実装担当）が設計に必要な範囲を調べる。体制・経路（auto・manual）・メインのモデルは別の項目で、互いに影響しない。

## 体制の選択

体制は人が3択で選ぶ。確認する側は、下の「メインの裁量」の3つの基準にもとづく推奨と理由を添えて、経路の確認とは別の一問で聞く。推奨の目安は次のとおり。

- LITE: 明確で局所的で、既存のテストで確かめやすい作業。
- ULTRA: 重要な契約、複数の技術領域、検証が難しい挙動に関わる作業。
- BASIC: それ以外の作業。

確認の規則は次のとおり。

- 確認するのは人への確認の窓口とする。Linear進行では[停止と人への確認](../linear/workflow.md)の経路の規則に従い、単独のdevではメインが行う。
- 各Issueの着手時と、人の指摘の一括修正を始めるたびに確認する。次の場合は聞き直さない: 依頼に体制が書かれている、利用者が範囲全体に体制を指定している、同じ修正単位を再開する、QAの差し戻しやコミット中の指摘で修正する、個々の指摘。
- 人の修正開始以外で始まる修正サイクルは、その作業で直近に選んだ体制を使う。
- 体制を変えたときは、新しく必要になった担当を新規に起動し、既存の成果と確定済みの判断・採否を引き継ぐ。レビューの回数はリセットしない。

## メインの裁量

メインは選んだ体制の必須担当に加えて、探索担当の配置、役割の追加、技術領域ごとの割り当て、並列化、複数担当の範囲分担を決める。BASIC・ULTRAでは、追加を次の基準で判断する（体制の推奨にも使う）。

- **不確実性**: 要件と既存の解法が明確か。責務・依存方向・設計案の比較に、下限を超える独立した検討が必要か。
- **影響範囲**: 局所的で利用側を追えるか。複数機能・共通基盤・実行環境をまたぐか。
- **失敗時の影響と検証可能性**: 容易に戻せて既存テストで確認できるか。認証・課金・データ保全などの重要な契約や、再現・検証が難しい挙動に関わるか。

点数・行数・一律の大小ラベルで人数を自動決定せず、未解決の問いと必要な独立確認に担当を対応させる。初期確認だけで分からなければ、まず探索の範囲を決め、その結果で設計前に体制を更新する。担当を起動するためだけの調査や計画書は増やさない。追加は必要な役割だけにし、どれか一つを増やすために全役割を増やさない。

LITEでは、探索を含む担当を追加しない。必要な調査・設計・簡素化・テスト・指摘の根拠の確認と修正は実装担当が、独立した確認は独立レビュー担当が担う。2名で足りないと分かったら、理由を添えて、人への確認の窓口からBASIC・ULTRAへの変更を相談する（変更の扱いは「体制の選択」のとおり）。

## 技術領域

技術領域は、Web・API・iOSのように技術や実装慣習が違う領域とする。配布先・写し・文書の分類は、別の技術領域に数えない。技術領域ごとに担当を置く場合は、全変更ファイルがちょうど1名の範囲に属するようにする。

## 記録と引き渡し

設計を始める前に、選んだ体制、追加した担当とその根拠、工程ごとの役割・人数・確認範囲、技術領域ごとに担当を置く場合はその割り当て、必須検証を短く記録する。独立レビュー担当は実装担当と別のコンテキストにする。

linear-executeから受けた作業では、選んだ体制と追加した担当を進行役へ報告する。追加の判断では人の承認を待たない。材料が欠けていれば初期確認して、BASIC・ULTRAでは追加の担当を決める。ローカル記録は `.shinaps/work/` 以下へ保存する。別セッションへは本文も渡し、相手から見えないパスだけに依存しない。

## 途中の増員

BASIC・ULTRAでは、選んだ体制は上限ではない。LITEでは増やさず、上の相談に従う。設計上の新しい不確実性、影響領域の追加、重要な契約への影響、検証失敗、指摘の対立が判明した時点でdevのメインが必要な役割・人数・確認範囲を増やす。担当からの提案はメインが判断する。理由と体制の変更を記録し、linear-executeでは進行役へ報告する。判断や報告のために作業を止める必要はないが、追加担当の確認が必要な工程は結果が揃うまで完了にしない。

- 新しい担当には現在の要件・同じ版の対象・規約・確定済み判断を渡す。独立確認を求める場合、他担当の今回の未確定結果は渡さない。既存担当の仕事を理由なく最初から繰り返さない。
- 増員で既存の未完了・不利な指摘を消さない。同じ対象への増員・交代でレビューラウンドの上限をリセットしない。枠不足は順番に起動し、人数を黙って減らさない。
- 体制判断は委託・モデル変更・操作・予算の許可を作らない。既存の許可と予算内の増員は再承認不要。仕様・範囲・明示された人数制限・許可・予算を変える必要がある場合だけ、人へ理由と選択肢を一問で確認する。

## 維持する条件

選んだ体制の必須担当を、自己確認・体制の表に無い兼務・メインの代行で完了扱いにせず、委託不可・起動不能なら未完了とする。明示された人数制限・予算が下限を満たさない場合は、人へ一問で確認する。合意があれば、実施しない必須担当を未実施として記録・報告し、品質上の完了とは報告しない。合意が無ければ未完了とする。独立レビュー担当の確認を、実装担当の自己確認で代えない。

要件と影響範囲の確認、必要なテストとプロジェクトの必須検証、適用規約の照合、全指摘の採否と根拠の記録を維持する。サービス規約を取得できない、担当が未完了、必須検証が失敗した場合はその状態を報告し、確認済みと偽らない。重大な未解決事項を完了にしない。linear-executeのLocal Agent QA、人レビュー、公開条件、終了地点は体制によって変えない。
