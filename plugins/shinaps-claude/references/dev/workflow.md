# dev の工程

Claude Codeのdev（`dev-claude`）の工程。役割・人数は[実装体制の判断](staffing.md)で選んだ体制の担当で進め（BASIC・ULTRAでは必須担当を下限に追加できる）、担当の起動・継続は[起動手順](launch.md)に従う。

## 1. 前提と作業記録

適用される `AGENTS.md`・`CLAUDE.md` と参照先、CI、既存スクリプトから作業条件を読み、依頼・範囲・操作許可を引き継ぐ。仕様を左右する不足だけ一問ずつ確認する。新しい恒久方針は了承を得て保存する。利用できないツールを仮定しない。

devの依頼は登録済みのdev役割への委託（Agentでの起動）を含む。委託しないのは、利用者が委託を明示的に禁止した場合と、Linear進行で[`dev_delegation`](../linear/configuration.md)がない場合だけ。worktreeは許可された場合だけ使う。委託が許可されない、または担当を起動・再開できず§2の交代もできない場合も、メインはその担当の作業（実装・修正・計画・検証・統合）を代わりに行わない。その工程を未完了として返し、必要な判断（許可・準備・体制）を求める。サービス規約を取得できない工程は未照合と明示する。

作業記録は `.shinaps/work/{YYYYMMDD-HHMMSS}-{slug}/` と `raw/` へ保存し、[共通手順](../work-records.md)に従って保全する。担当の応答は全文を参照できる形で保存し、対象版・役割・担当ID・確認範囲・完了状態を対応づける。短い作業は短い計画・記録にする。

## 2. 役割と継続

下の表は各役割の工程と継続を定める。起動する担当と人数は、選んだ体制の表（`staffing.md`）に従う。

| 工程 | 役割定義 | 継続と責任 |
| --- | --- | --- |
| Phase 2 | `shinaps-explorer` | 置く場合に、必要な探索範囲ごとに起動 |
| Phase 3・4・6・7 | `shinaps-architect` | 担当1は設計・統合・設計適合性・指摘統合・修正計画と、人の指摘の技術調査（読み取り専用）を継続。担当2以降は独立設計と追加確認のみ |
| Phase 4 | `shinaps-plan-reviewer` | 修正版の再確認も同じ担当 |
| Phase 4・6 | `shinaps-simplifier` | 計画の簡素化は修正版の再確認も同じ担当。実装の簡素化は計画とは別の担当で、ラウンドと修正サイクルをまたいで継続 |
| Phase 4・6 | `shinaps-review-verifier` | 指摘検証担当を置く体制で、検証ラウンド（計画確認と実装後レビューの各ラウンドに1回）ごとに新規。今回の指摘を出した担当を流用しない |
| Phase 3・5・7 | `shinaps-implementer` | 1体。修正も同じ担当。設計担当を置かない体制（LITE）では、設計責任者として計画と指摘の整理・採否も担う |
| Phase 6 | `shinaps-reviewer` | 独立コードレビューは実装担当とは別で、レビューラウンドごとに新規。独立コードレビューを含む複数の種類を兼ねる場合は、独立コードレビューの規則に従う。可読性・慣習レビューを技術領域ごとに置く場合は、ラウンドと修正サイクルをまたいで継続し、技術領域が増えたら追加 |
| Phase 6 | `shinaps-refine-agent` | refine 担当を置く体制で、ラウンドと修正サイクルをまたいで継続 |

- 異なる役割と独立比較の担当は別コンテキストで起動する。担当番号を起動前に固定し、同じ役割の継続は同じIDを使う。再開できない場合（resumeをまたぐ場合を含む）は同じ役割へ既存の成果・最新の差分・未解決点を引き継いで交代を記録する。
- 目的・範囲・規約全文・必読ファイル・今回の役割・担当番号・確認対象の版・成果物のパス・引き継ぎ先を依頼に渡す。実装担当にはファイルの所有範囲を明記し、他者の変更を戻さず現物に合わせるよう伝える。他の担当は読み取り専用で、自分でエージェントを起動しない。
- 独立確認する担当には同じ版の入力を渡し、今回の他担当の結果を読ませず意見交換させない。継続担当には前回の確定済み指摘と採否を渡してよい。対象を編集中にレビューせず、全結果が揃うまでメインと実装担当も対象を変えない。外部変更が入れば影響範囲を同じ最新の版で確認し直す。
- メインは依頼の確認、体制と工程の調整、担当の起動・待機・全文保存・引き渡し、結果と未解決事項の取りまとめ、利用者判断の取り次ぎを行う。実装・修正、指摘の技術的検証と採否、設計適合性の実コード照合、既存の証拠がある検証の再実行は引き取らず、担当に割り当てた判断を先回りして選別しない。起動失敗・空回答・未確認範囲を「指摘なし」にしない。
- devの完了後に同じ会話・sessionで来る依頼（対話の次のターン、resume、Bridge、人の相談、QA差し戻し）も同じdevの分担で扱う。メインは確認済み結果の説明・質問の整理・取り次ぎだけを行い、調査・技術的検証・編集は担当へ渡す。初回devの完了・短い追加依頼・通常の会話への復帰を例外にしない。Codexが[UIの微調整](../linear/workflow.md#codexによるuiの微調整)で返した差分は、同じ分担で取り込み、現在の工程の差分として検証し、既存のレビューを続ける（回数はリセットしない）。
- **修正サイクル**: devの完了後に実装の修正が必要になったら（人の修正開始（[人のレビュー](../human-review.md)）、Codex QAの差し戻し、コミット中の指摘など、契機によらず）、未対応の指摘の集合を一つの入力にして次の順に進める。人の修正開始では、体制を[体制の選択](staffing.md)に従って確認する。入力が一致する結果は[テスト方針](../testing.md)に従って引き継ぐ。一部をコミットした後の修正は `commit` の規定どおり後続単位にする。
  1. 設計責任者が修正計画と、影響を受ける工程を決める。
  2. 設計・契約・検証条件を変える場合だけ、Phase 4の扱いで再確認する。
  3. 同じ実装担当が修正する（Phase 5）。
  4. Phase 6の担当（選んだ体制のとおり）と、指摘検証担当を置く体制ではその新規の担当が確認する。範囲は修正とその影響範囲とし、確定できなければ広げる。
  5. Phase 7で統合・修正する。

## 3. Phase 1: タスクと体制の確定

依頼・引数・指定された成果物から目的・受入条件・範囲を確定する。確定済みの内容を聞き直さず、依頼されていない過去の作業を始めない。成果物に実装可否の状態があればreadyを確認し、欠落・不明なら変更内容を推測せずタスクを確定する。内容ハッシュがある根拠は現在値と照合し、古い根拠は読み直す。

Issue・既存spec・調査記録・関連コード・検証方法を必要な範囲だけ確認する。依頼に書かれた体制（無ければ[体制の選択](staffing.md)に従って確認する）の担当で進め、BASIC・ULTRAではlinear-executeから受けた材料と現物からメインが追加の担当を決める。設計担当を起動する前に、選んだ体制・追加の担当と根拠・役割別人数・技術領域ごとに担当を置く場合はその割り当て・必須検証を作業記録の `staffing.md` へ保存し、短く報告する。不足する調査があればPhase 2で補い、体制を更新する。

## 4. Phase 2: 規約と必要な探索

規約はメインが取得し、以降の担当へ全文を渡す。担当はShinaps MCPを呼ばない。

- `list_search_facets` でfacetを確認し、`search_rules` に現在のrepoOwner・repoNameと対象に関連するfacetを渡す。manifest・lockfileなどで確認できた対象バージョンだけ `projectVersions` に指定する。確認できない場合は共通ルールのみの照合と記録する。
- プロジェクト規約と関連docs、引き継いだ調査の必読ファイルを確認する。時間に依存する根拠が判断に影響する場合は公式情報で確かめる。
- 十分な根拠があれば探索担当を追加しない。不足する領域は、LITEでは実装担当が調べる。BASIC・ULTRAでは探索担当を置くか、各設計担当が自分の設計に必要な範囲を調べる。探索担当には既存成果物と不足する問いを渡し、`raw/explorer-{n}.md` に結果を保存する。

新しい不確実性・影響範囲が見つかったら、設計前に体制を更新する。

## 5. Phase 3: 設計と計画

設計責任者は設計担当1、設計担当を置かない体制（LITE）では実装担当とする。目的・受入条件・調査結果・規約・既存配置を踏まえ、変更後の責務・依存方向・利用側・外部契約・実装順・検証を決める。計画には目的・不変条件・変更範囲（対象ファイルと責務）・実装順・検証を書き、個々の置換や文言は実装担当が現物に合わせて決める。構造変更が必要なら含め、単に変更量が少ない案を優先しない。不要な変更と仮想的な汎用化は避ける。

設計担当が複数なら同じ入力で独立に検討させ、全結果の後に担当1が根拠とトレードオフを比較して一つの案へ統合する。多数決にしない。各結果は `raw/architect-{n}.md`、統合案は `raw/architect.md` に保存する。LITEでは実装担当が短い計画と検証方針を作り、報告の冒頭に書く。

## 6. Phase 4: 計画の確認

計画レビュー・計画簡素化の担当を起動し、同じ計画・要件・調査・規約を渡す。LITEではこの工程を起動せず、計画はPhase 6の独立レビュー担当が、計画自体も誤りうる前提で確かめる。レビューは要件・実現可能性・設計リスク・検証方針、簡素化は目的と外部契約を保って減らせる構造・状態・手順を確認する。

全結果を `raw/plan-review-{round}-{n}.md` / `raw/plan-simplify-{round}-{n}.md` に保存し、「指摘の検証と統合」に従う。計画変更があれば `raw/architect-revised-{round}.md` に残し、変更の影響を受ける担当へ同じ修正版と前回の採否を渡し、修正箇所と影響範囲を中心に再確認させる。影響範囲を確定できなければ再確認の範囲を広げる。契約・設計・検証条件に影響しない表記整理だけで新たなラウンドを作らない。

採用すべき指摘と必要な判断が解決したら `plan.md` を確定する。計画段階には回数上限を設けないが、目的のない反復や新しい根拠のない却下案の再提案は行わない。runtime固有の上限があれば起動手順に従い、未確認の最終変更と残課題を明示する。

## 7. Phase 5: 実装と検証

メインは `plan.md` を再読し、実装担当1体へ目的・確定計画・必読ファイル・規約全文・設計判断・所有ファイル・既存差分・必要な検証を渡す。実装担当が編集中はメインも同じ範囲を編集しない。

実装担当は計画を実装し、仕様を保つ簡素化・セルフレビュー・[テスト方針](../testing.md)に沿った必要な検証を行う。仕様上の不明点や計画と現物の矛盾は変更を広げず報告する。技術的な矛盾はメインが設計責任者へ渡す。仕様・範囲の変更はメインが人に確認する。通常の判断は既存の合意と規約で解決する。検証でSimulator等の仮想端末を使う場合は、[QAと証拠](../linear/qa.md) の「Simulatorの所有と再利用」に従う。

実装ミスによる検証失敗の自己修正は3回まで。超えた場合は根拠と未解決点を返し、メインが追加試行・差分のレビュー・計画への差し戻しの選択肢を人に確認する。

メインは報告の対象版・範囲・完了状態と、検証の証拠の所在・終了コードを照合して `implementation.md` に保存する。全文の再レビューや同じ版の検証の再実行はせず、不足や矛盾は当該担当へ戻す。内容は変更と設計理由、重要な判断、計画からの変更と合意、検証結果、未実施事項。UIレビューはこの工程に含めず、linear-executeのAgent QA等で扱う。

## 8. Phase 6: 実装後の確認

同じ差分を固定し、選んだ体制の担当と追加した担当を並行して起動する。技術領域ごとに可読性担当を置く場合は、全変更ファイルがちょうど1名の範囲に属することを確かめ、足りない技術領域があれば担当を足す。複数担当なら確認範囲を明記し、重大な契約の独立確認を分担だけで置き換えない。

| 観点 | 責任者と入力 |
| --- | --- |
| 設計適合性 | 設計担当1を再開（LITEでは独立レビュー担当）。計画・受入条件・責務・依存方向と実コードを照合 |
| 独立コードレビュー | 新規の `shinaps-reviewer`（独立コードレビュー）。対象コード・全差分・利用側・規約・検証結果を読み、計画自体も誤りうるものとして正しさ・安全性・性能を確認 |
| 規約照合 | `shinaps-refine-agent`、またはBASIC・LITEでは独立コードレビューの担当。規約全文・対象ファイル全文・変更範囲を照合 |
| 実装の簡素化 | 実装の簡素化の `shinaps-simplifier`（LITEでは独立レビュー担当が兼ねる）。目的・契約を保って削除・統合できる内容を確認 |
| 可読性・慣習 | 体制の表の担当（ULTRAでは技術領域ごとの `shinaps-reviewer`（可読性・慣習レビュー）、BASIC・LITEでは独立コードレビューの担当が種類を複数指定されて兼ねる）。担当する範囲の差分と対象ファイルの現状全文、規約、計画に記した先例、合意済み仕様を渡す |

LITEでは、独立レビュー担当を両方の種類で起動し、設計適合性と簡素化もあわせて依頼する。

変更言語・領域・バージョンがPhase 2の規約の範囲を超えた分だけ取得を補い、同じ全文を渡す。staged・unstaged・untrackedを含めて対象を特定し、新規ファイルも確認する。設計担当1は自身の確認が終わるまで他担当の今回の結果を読まない。

結果を `architecture-review.md` / `review-{round}-{n}.md` / `raw/refine-{round}.md` / `raw/simplify-{round}-{n}.md` / `raw/readability-{round}-{n}.md` に保存する。未確認部分があれば同じ担当へ戻し、全結果が揃ってから検証・統合する。

## 9. 指摘の検証と統合（Phase 4・6共通）

指摘の整理は、設計責任者が採否を決める前に、指摘検証担当を置く体制では検証ラウンドごとに新規の `shinaps-review-verifier` が行い、いない体制では設計責任者が行う。全レポート全文・出典・確認範囲・要件・対象版・規約・検証結果を使い、根拠・誤認・重複・対立・未確認を区別する。元の項目を消さず出典IDを保持する。指摘なしの担当は完了と確認範囲を確認する。

検証結果は `raw/plan-verification-{round}.md` または `raw/implementation-verification-{round}.md` に記録し、verifierが整理した場合は設計責任者へ全文を渡す。設計責任者が全項目の採否と理由、必要な計画修正・実装修正・検証を一つにまとめる。複雑な指摘や対立があれば `staffing.md` に従い担当を追加する（LITEでは体制の変更を相談する）。

統合は多数決ではなく根拠で行う。設計責任者は自分の成果物への指摘も根拠で採否を決めて理由を記録し、その確認を独立検証とは報告しない。事実の食い違いや根拠不足で判断できない指摘だけ指摘元に確認し、Infoや提案を採らないことに同意を求めない。指摘元への確認は同じ担当の継続で行い、レビューのラウンドに数えない。仕様・受入条件・ユーザー体験の変更や許可範囲の拡大は人の合意前に採用しない。verifierが整理した場合、設計責任者は検証済みの全件の事実確認を最初からやり直さない。

## 10. Phase 7〜8: 修正と終了判定

設計責任者の修正指示を同じ実装担当へ返し、変更と必要な検証を `fix-log.md` に記録する。Local Agent QAの後の修正では、[変更記録](../linear/qa.md#qaの時点対象最終qa)の項目も残す。修正不要ならPhase 9へ進む。

実装後の全体レビューは、最初のdevと各修正サイクルのそれぞれで、初回を1として最大2ラウンド。同じサイクルの中の増員・交代・計画変更では上限をリセットしない。1回目の後に修正したら、同じ最新差分でPhase 6の体制に必要な増員を加えて2回目を行い、検証・統合する。2回目は修正箇所と影響範囲を中心に確認し、影響範囲を確定できなければ確認範囲を広げる。範囲を絞った場合も必須検証は全体で実行し、完了前に設計責任者が全差分を計画・受入条件と照合する。2回目の後に修正したら必要なテストを行い、3回目の全体レビューは起動せず、最終差分が再レビューされていないことを報告する。

重大な未解決事項、必須検証の失敗、必要な担当の未完了が残れば品質上の完了とは報告しない。

## 11. Phase 9: 完了と引き渡し

選んだ体制・追加した担当と変更理由、実際の担当・確認範囲と必須担当の完了状況（合意による未実施を含む）、計画と実装後のレビュー回数、採否・修正、検証結果、未実施・未照合・未解決事項を報告する。refine 担当を置かない体制（BASIC・LITE）では、規約照合を独立コードレビューの中で行い、ファイルごとの完了一覧が無いことを書く。修正サイクルの後は、初回の報告項目を最新にし、対応した指摘と採否・再実施した工程・[変更記録](../linear/qa.md#qaの時点対象最終qa)を加える。

linear-executeから受けた作業は未コミットの差分と結果を進行役へ返す。devの完了はLocal Agent QAへの引き渡しであり、進行全体の終了ではない。[Linear共通設定](../linear/configuration.md)と[担当と工程](../linear/workflow.md)に従い、autoはQA後の差分確定の依頼を受けて、manualは人のコミット開始依頼で `commit` を始め、単位の退避・stage・commitはQA結果の引き渡し後に行う。auto経路は [Claude CLI](../linear/claude-cli.md) のresultへ報告し、同じsessionのresumeで質問・修正を受ける。manual経路は同じ対話セッションで人と作業し、[Bridge](../linear/bridge.md)で依頼元Codexへ報告する。manualの完了時は、修正サイクルの後も含めて、人へユーザーのレビュー待ちと明示する（[manualの手順](../human-review.md)）。

単独のdevではコミットが許可されている場合だけ範囲とモードを `commit` へ渡す。許可がなければ未コミットで返し、形式的な許可確認を追加しない。PR・リリースも許可された範囲で各スキルへ渡す。単独devにLinear進行・新しいゴールを必須にしない。

explore・spec・review・debugからの成果物は入口の引数で直接渡す。専用の引き継ぎファイルは作らず、Phase 1・2で既存成果物を再利用する。
