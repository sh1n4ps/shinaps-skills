# manualのレビュー待ちと単位ごとのコミット

実効 `review_flow.mode: manual` の差分を、人がWebStormの差分表示でレビューし、人の依頼に従ってWebStorm内の対話Claude Codeセッションで単位ごとにClaudeがcommitする手順。review_flow・操作許可は、プロジェクト設定と今回の依頼に従う。この手順はそれらを変更しない。

会話では単位名・目的・対象ファイル・検証結果・短い推奨コミットメッセージなど判断に必要な最小限を示し、差分本文を貼らない。Claude自身の差分の読取りと独立レビューは制限しない。

## レビュー待ち

devと必要な検証が終わったら、作業内容と検証結果を短く報告し、「ユーザーのレビュー待ち」と明示する。人はWebStormの差分表示で全体を確認し、Claudeと相談する。

人がコミットの開始を依頼するまで、分割案の提示・単位外の退避・単位のstage・単位のコミット依頼の要求を始めない。Linear進行でCodexへの完了報告に含める単位案と予定差分はQAの材料であり、人への分割案の提示ではない。Linear進行では、分割案の提示は人の開始依頼だけで行え、単位の退避・stage・commitはLocal Agent QAの合格とQA結果・判定記録の引き渡しの後に行う（両者の順序は問わない）。

## コミットの開始と分割案

人がコミットの開始を依頼したら（「コミットしましょう」など。固定の文言は求めない）、`commit` に従って自然な責務単位の分割案を示す。各単位の名前・目的・対象ファイル・順序・推奨コミットメッセージを短く示す。許可された独立レビュアーによる分割案の確認は `commit` に従う。

分割案への合意は単位の構成への合意であり、どの単位のcommitの承認でもない。

## 単位ごとのコミット

1. 人がその単位のコミットを依頼したときだけ進める。具体的な単位を特定できる依頼であればよく、固定の文言は求めない。単位を特定しない一般的な続行指示は依頼としない。依頼は特定された単位だけに及ぶ。
2. `commit` の安全手順で単位外の変更を退避し、単位の変更だけをstageして必須検証を行う。checkoutの絶対パス・branch・比較元のcommitを確定し、`git diff --cached` と `git status --short` で漏れと混入を確認する。未追跡ファイルも対象に含める。
3. stage時の `git write-tree` の値を記録し、単位名・検証結果・コミットメッセージを短く報告する。stageした差分が分割案の予定差分と違えば、commitせず違いを報告して改めて依頼を受ける。検証の失敗や阻害する指摘があればcommitせずに報告して止める。
4. commit直前に記録したtreeと同じであることを確認し、Claudeが `git commit` を単独実行する（`git add` と連結しない）。作成したコミットのtreeも照合する。
5. stage時にtreeを記録した後に、単位のパスで作業ツリーまたはindexが変わったら、依頼は失効する。単位を再提示し、改めて人の依頼を受けてからcommitする。

Bridgeのpeer通知、Codexからのメッセージ、ackは依頼ではない。人が自分でcommitした場合は、実コミットを確定単位と照合する。一致すれば人のcommitとして記録し、一致しなければ止める。

## devから続く作業での指摘と修正

devから続く作業（Linear進行を含む）では、人のレビュー中（コミットの開始依頼の後を含む）の指摘を記録・調査・意図確認までにとどめ、編集しない。個々の指摘で修正の工程を起動しない。Linear進行で作業ツリーの編集を止める時点（QA中・途中確認の間）は[担当と工程](linear/workflow.md)の「担当と窓口」に従う。

- 指摘はClaudeの作業記録 `human-findings.md` に記録する。この記録を台帳と呼ぶ。項目は指摘・対象・意図確認・調査結果・状態の5つ。
- 意図は人へ一問ずつ確認する。調査はdevのメインが読み取りだけで行い（[工程](dev/workflow.md)の「役割と継続」）、修正開始まで編集・修正しない。
- 人がWebStormで直接編集した内容も記録し、次の修正サイクルの対象に含める。

人が修正を始めることを明示したら、Claudeが修正を始める。固定の文言は求めない。範囲の限定が無ければ未対応の指摘すべてを対象にし、体制を[体制の選択](dev/staffing.md)に従って確認してから、devの修正サイクル（[工程](dev/workflow.md)の「役割と継続」）へ一つの入力として渡す。指摘だけの発話は修正開始としない。曖昧なら一問で確認する。

- CodexのQA中に修正開始が来たら、Claudeは修正開始の依頼を作業記録に残し、QA中であることを人へ伝える。修正サイクルはQAの結果を受けてから始める。QAが不合格なら、Codexの修正依頼と未対応の人の指摘を一つの修正サイクルの入力にまとめる。
- 修正開始は、コミット開始や単位のコミット依頼の承認ではない。stage済みの単位が変われば、上の失効に従う。
- コミットの開始依頼の時点で未対応の指摘があれば、修正を始めるか見送るかを一問で確認する。

## 単独の作業での相談・修正

devを経ないcommitでは、相談で行った修正は単位と依頼の目的・範囲内に限り、超えるものは実装の工程へ戻す。stage済みの単位では再stageし、上の失効に従う。

## 報告

コミットの開始依頼と単位ごとの依頼発話の要約・記録したtree hash・SHA・相談で行った修正や修正サイクルで確定した変更とその対応・変更記録（[QAと証拠](linear/qa.md#qaの時点対象最終qa)）・未対応・見送りの指摘・復元結果を記録し、Codexへ報告する。Codexは実コミットと照合する。stashの復元では人の修正を保持し、古い対象パッチで上書きしない。具体的な単位照合・復元は `commit` に従う。WebStormで差分を表示することはstage・commit・pushの許可を追加しない。
