# Issueの整理と記録

本文は最新の要件と結論を保ち、古い案や相反する追記を残さない。現在の工程・次の担当・お願いを書く欄（移行元のテンプレートにある「現在地」など）は本文に設けず、整理・更新するIssueにあれば内容をステータスとコメントへ移して欄を除く。工程はステータスで表す。残作業・待ち理由・次の担当は、QAコメントか待機時のコメントで表す。チームに既存の本文規約があればその形式を尊重し、下のテンプレートの各欄の役割を対応づける。

共通ルールはスキルとリポジトリ、製品仕様はその正本、個別Issueの判断と結果はIssueに置く。共通手順をIssueへ転載しない。

## 着手前に作業をIssueへ紐づける

作業先リポジトリの規約が作業のIssueへの紐づけを求める場合、または利用者が紐づけを明示的に依頼した場合に、この手順で紐づける。進捗・完了を管理する作業は、開発・調査・運用・設定変更・文書整理を問わず、またGit変更の有無にかかわらず、実作業の着手前に一つのIssueへ紐づける。原則として一つの目的を一つのIssueで管理する。その場の質問・相談・短い状態確認と、紐づけたIssueの中の細かな手順には新しいIssueを作らない。相談から実作業へ移る時点で適用する。紐づけに必要な設定の確認・初期設定と、そのためのIssueの読み取り・検索・整理は紐づけの一部であり、それ自体のIssueを作らない。

1. 作業先リポジトリと、紐づけ先のworkspace・team・projectを決める。紐づけ先は、[configuration.md](configuration.md) の「設定の読み方」に従って読んだ作業先リポジトリの設定の `target`、または利用者がその場で指定した先にする。
2. 決めた先で、目的と作業先に合う既存Issue（依頼で示されたIssue、未完了のIssue、作業を含む親・関連Issue）を探し、あれば再利用する。作業が既存Issueの範囲に入る場合は、そのIssueの中の手順として扱う。
3. 該当がなければ、利用者から任された目的について、下の「共通Issueテンプレート」に従って作成する。作成は、呼び出し元の `linear-plan` / `linear-execute` と [configuration.md](configuration.md) の「許可」で認められた範囲だけで行う。新しいIssueをCycleへ入れるのは、既存の合意か明示依頼がある場合だけにする（「Cycle・期限・見積もり」）。作成の後は読み戻し、結果が不明なら現状を確かめてから再試行し（「要件を整理する手順」）、同じ目的のIssueを重ねて作らない。
4. 使うIssueのリンクを、会話またはBridgeの依頼・報告に示してから実作業に入る。

紐づけ先が決まらない、接続できない、または新しいIssueの作成が必要だがその許可がない場合は、別のworkspace・team・projectや別のリポジトリの設定で代わりに作成・更新しない。紐づけを必要とする実作業の前で止まり、理由と必要な判断・準備（作成の許可がない場合はIssue案）を利用者に伝え、回答を得てから再開する。

Issueの作成・紐づけは作業の記録であり、担当・人のレビュー・終了地点・継続の範囲を変えない。コミット・push・公開・外部への送信の許可を追加せず、開発進行・Cycleの継続・ゴールの設定を始めない。

## 要件を整理する手順

1. 正しいアカウント・workspace・teamで、本文・親子・依存・Cycle・ラベル・状態・コメントを読む。一覧は最後のページまで取得する。関連仕様の正本・実装・会話の合意と照合する。
2. 一つのIssueを、独立してレビュー・受入できる到達点に絞る。分割が必要なら既存Issueを優先して責務を移し、引継ぎ元と引継ぎ先、依存を更新する。元の要件ID・重要な判断・検証証拠を失わない。
3. 確定・暫定・未決を区別する。既存の根拠で解消できる曖昧さや重複は自分で整理する。利用者の判断が必要な仕様変更や矛盾だけを一問ずつ相談する。未決の要件を推測で確定しない。
4. 受入条件は場合の列挙ではなく、満たす性質で書く。Agent QAとHuman QAに分ける。
5. 着手の前提と最終受入の前提を区別し、実際のブロッカーだけを依存に登録する。
6. 更新後に本文・状態・ラベル・依存を読み戻す。失敗や結果不明なら現状を確認し、未反映分だけ再試行する。

## Readyの条件

目的・範囲・受入条件が明確で、自分たちの作業を依存順に進めれば着手できる。前工程の実装待ちだけを理由に未整理へ戻さない。Readyの後に前提が崩れたら、理由を記録して、整理中または該当する待ち状態へ戻す。

## Cycle・期限・見積もり

| 作業 | 作成時のCycle |
| --- | --- |
| すぐ着手する作業 | 現在のCycle |
| 今後実施する作業 | 見積もり・依存・期限・作業量から決めた予定のCycle |
| 時期未定の案 | Backlogに置き、Cycleを設定しない |
| 取りまとめだけの親Issue | CycleとEstimateを付けない |

- 期限は「いつまでに必要か」、Cycleは「いつ取り組むか」を表す。前提作業を後続のCycleに置かない。時期未定の案に予定を作らない。見積もり・期限・Cycle範囲の変更は、既存の合意または明示的な依頼の範囲でだけ行う。
- 依存Issueを作るのは、独立した担当・完了条件が必要な作業だけ。既存のIssueを優先する。機能専用ならサブIssue、共有の準備なら独立したIssueにする。

## 共通Issueテンプレート

```markdown
## 背景・目的
今の困りごとと、それを解決する理由。

## できるようになること
誰が何をすると、何ができるようになるか。変更前と変更後の操作・結果・制約を、技術の説明を読まなくても分かるように書く。画面のない変更は、利用する人や運用への効果として書く。

## 実装方針
「できるようになること」をどう実現するかの短い設計。責務の分担、データの流れ、既存構成の変更を書く。作業先のリポジトリ名もここに書く。前提、依存するIssue、根拠（仕様の正本・要件ID・詳細設計）への参照は、ここか関係する欄に書く。ファイルの一覧や作業手順だけで設計の代わりにしない。

## 受入条件
### Agent QA
- [ ] 満たす性質 — 確認方法・工程・環境
### Human QA
- [ ] 人が確認する性質 — AIだけでは確認できない理由・環境
（不要なら「不要。」だけを記載）
```

- 「実装方針」の作業先のリポジトリ名は、同じprojectを複数のリポジトリが使うときに、適用する設定を決めるために使う。ローカルの絶対パスは書かない。
- Linear側のテンプレート設定を変えることは別の設定操作である。本文への適用では変更しない。

## 書き方

- 一つの欄で一つの疑問に答え、空欄や定型文で埋めず、同じ情報を複数の欄に書かない。判断の要点（採用した案と理由、未決事項）は該当する欄の本文に書き、詳細な設計は参照先に置く。途中の議論と検証の詳細はコメントへ残し、採用した結論を本文へ統合する。長いログを本文へ貼らない。
- Issueの範囲は[共通ルール](workflow.md#失敗・許可・停止の共通ルール)のとおり目的・変更内容・受入条件から判断するので、範囲外の一覧は作らず、誤解されやすい境界だけを該当する欄に書く。
- 「できるようになること」の説明に必要なら、画面はデザインやスクショ、操作や遷移は短い動画、画面のない処理は入出力の例を添える。
