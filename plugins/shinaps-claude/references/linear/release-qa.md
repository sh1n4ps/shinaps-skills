# リリースQAの引継ぎと進行

develop へ統合した開発Issueの確認を、develop → main の release PR ごとのリリースIssueへ集めてから配布する方式（以下「この方式」）の手順。開発Issueの引継ぎの書き方と、リリースIssueを進める担当の判断を定める。記録の追記と照合は共通のCLIが行い、どの項目をどう確かめるか、以前の合格を今の head へ持ち越してよいかは担当が決める。

| 担当 | 責務 |
| --- | --- |
| 進行役（Linear進行ではCodex） | 開発Issueの引継ぎの記録、リリースIssueの開始時の決定・計画・確認・記録・ステータス・Done |
| 共通のCLI | 引継ぎの収集、記録の追記、記録と release PR の head・環境の版の照合、`release-gate`、release PR の merge |
| 作業先のリポジトリ | CLIを呼ぶwrapper、環境の版を読む観測コマンド、配備・配布の手順、CLIを実行するworkflow（GitHub Actions）、記録として認めるLinearの利用者の設定 |
| 人 | 人が行う確認、許可の範囲の判断 |

`release-gate` は、共通のCLIが release PR の head に付ける判定で、stagingの確認が記録の上でそろったかを表す。満たしていない条件は `status` が理由として示す。

Linear進行では、Claudeは実装担当のままで、リリースIssueの進行を担当しない。リリースQAで見つかった不具合は、元の開発Issueに関連づけた修正Issueとして通常の工程でdevelopへ入れる。

## 採用の判定

作業先の設定が採用した資料（`instructions.md` と `references`。[設定の読み方](configuration.md#設定の読み方)）が、release PR とwrapperの呼び出し方を定めている場合だけこの方式を使う。ファイルやworkflowがあるだけで採用とは扱わない。定めていない作業先は[担当と工程](workflow.md#工程とステータス)の5工程で進め、この方式への移行を求めない。採用する前から進行中のリリースは途中で変換せず、その完了か、明示した切り替えの時点から使う。

- 操作を行うかどうかは[依頼範囲と操作](../request-scope.md)で判断する。この方式は許可を増やさず、許可のための設定も持たない。
- `status`・`plan`・`record`・`carry`・`record-deployment`・`merge` は作業先のwrapperで実行する。`sync`・`gate` は作業先のworkflowを起動して実行する。共通のCLIの配布元と版は作業先の資料に従い、本書では決めない。
- 共通のCLI・wrapper・workflowの失敗や拒否は、成功を記録せずに止め、実際の状態を読んで成功した工程から再開する。記録だけが失敗したら記録だけをやり直し、配備・配布はやり直さない。起動したか分からない配備・配布は、環境と配布先の実際の状態を読んでから進める。記録として認められない利用者の記録など、作業先の設定が原因の拒否は回避せず、[停止と人への確認](workflow.md#失敗確認停止の共通ルール)に従う。

## 保つ性質

- developへ統合した変更の受入条件は、開発中に確かめた証拠、引継ぎの項目、理由付きの「なし」のどれかへ辿れる。空の一覧や未整理を、確認不要とは扱わない。
- 一つの操作で複数の項目を確かめても、結果から各項目と出所の開発Issueへ辿れる。
- 記録は追記だけにする。確かめ直した結果は新しい記録にし、変更の影響が無いと判断した項目は、理由を付けた `carry` で以前の合格を今の head へ持ち越す。以前の記録を書き換えない。
- 人が確かめると決めた項目は、本人の報告にもとづく記録だけで満たす。開始時の許可、agentの合格、自動の承認では満たさない。
- 配布の成功、環境で実際に動いている版、QAの合格は別の事実として扱う。
- 共通のCLIの判定と表示（`release-gate`、項目の状態）はLinearの工程ではない。リリースIssueのステータスとDoneは、進行役が結果を読んで動かす。

## 開発Issue: リリースへ引き継ぐ確認

開発IssueのDoneは、必要なQA・レビュー・developへの統合・引継ぎがそろった状態を表し、配布済みを意味しない。通常のPRのbaseはdevelopにし、PRのタイトルか本文に開発Issueのキーを書く（ブランチ名だけでは出所に辿れない）。

進行役は、Local Agent QAの合格後、終了地点で止まる前（遅くともdevelopへmergeする前。収集はdevelopへのpushのたびに引継ぎを読む）に、開発Issueのコメントとして引継ぎを書く。材料は受入条件、Local Agent QAの記録、ソースの差分、Claudeの完了報告（未解決の事項など）。

- 開発中に確かめられる条件は開発Issueで確かめ、引継ぎで後へ回さない。配布物・staging・本番・人・実機でしか確かめられない条件と、配布した環境で確かめる価値のある利用者向けの挙動は引き継ぐ。どちらでも、環境が無いことを理由に条件を消さない。
- 見出しは `リリースへ引き継ぐ確認`（階層は問わない）。最上位の箇条書き1つが1項目で、入れ子や続く段落は同じ項目に含まれる。各項目には、操作と期待結果、stagingか本番か、人や実機が要る条件、開発中に確かめたことと未確認のことを普通の文で書く。確かめる環境や担当（agent・人）が違う確認は、別の項目にする（計画は項目ごとに担当を一つ持つ）。
- 全項目に共通する条件は、最初の箇条書きより前に書く。項目ごとに違う条件は、その項目の中に書く。
- 追加の確認が要らなければ、節を `なし: <理由>` だけにする（他の項目や導入文と混ぜない）。理由の無い「なし」と空の節は未整理になる。
- 人にJSON・内部のid・短縮したidを書かせない。項目のidは共通のCLIが内容から作る。

```markdown
### リリースへ引き継ぐ確認

テスト用のアカウントでログインして確認する:

- staging で一覧画面を開くと、新しい順に並ぶ
- staging で通知を受け取ると未読の件数が増え、アプリをバックグラウンドから戻したときも増える（開発中は Simulator の通知で確認済み。実機は未確認）
- 本番の配布後に、実機で初めて起動すると通知の許可を一度だけ求められる（人が確認する）
```

最新の節が全件を表すので、直すときは以前の項目も含めた節を新しいコメントで書く。項目や導入文の文言を変えると別の項目として扱われ、以前の合格は付かない（導入文の変更は全項目に及ぶ）。developへmergeした後に直したら、作業先の手順で `sync` を起動する。他のコメントではこの見出しを使わない（最新の引継ぎとして読まれる）。折りたたみの節は引継ぎの節より後に置く（節は、同じ階層以上の次の見出しか折りたたみの区切りで終わる）。

## リリースIssueの進行

リリースIssueは、developへのpushで共通のCLIが release PR とともに作る。開発Issueの着手から差分確定まで（Readyの判定、経路・体制の確認、Claudeへの依頼）は通らず、この節の工程で進める。[失敗・確認・停止の共通ルール](workflow.md#失敗確認停止の共通ルール)・[待ち状態](workflow.md#待ち状態)・[人への依頼](workflow.md#人への依頼)は使うが、不合格の戻し先は冒頭の修正Issueにする。リリースIssueは修正Issueへの依存として元の工程のまま待ち（[待ち状態](workflow.md#待ち状態)）、修正Issueは今回の実行範囲に含まれる場合か、利用者と合意した場合に進める。

バックログ消化・Cycle全体の対象には、利用者が対象として明示した場合だけ含める。開始時の対象一覧にリリースIssueがあり明示されていなければ、対象外として理由とともに[開始時の記録](execution.md#開始時に固定するもの)に残し、Cycle報告では成果と区別する。

### 到達点と開始

到達点は、今回の明示の指定を優先する。一般的な進行の依頼では、設定の `stop_after` が `issue_done` ならDoneまで進む。他の値はリリースIssueに対応する工程が無いので、[工程とステータス](workflow.md#工程とステータス)の「適用される最後の必要工程まで」を当てはめず、開始時に一問で確認する。release PR のmergeで配備が始まる作業先では、その配備が到達点に含まれるかを[依頼範囲と操作](../request-scope.md#通常操作)で照らす。

開始時に、リリースIssueの本文（共通のCLIが作る本文がここに書くよう案内している。共通のCLIは作成後の本文を書き換えない）へ次を書く。

- 配布先（作業先の資料か受入条件にある先）と到達点。資料と受入条件から今回の配布先が一つに決まらないときは、開始時に一問で確認し（到達点の確認が要るときはそれと合わせる）、回答を残す。
- 人の担当
- 必須のQA: 項目の外で行う確認（共通の導線、本番での環境差と主要な導線など）とその環境。項目ごとの要否は共通のCLIの計画の記録（表示用コメントで確かめられる）にあると書き添える。

項目ごとの要否は計画の記録を正本にし、本文へ写さない。途中で変えたら本文を直し、理由をコメントに残す。到達点までの通常操作は、本番の直前に許可を取り直さない。

### 計画

`status` の出力（以前のheadからの変更を含む）を読み、項目の重複・順序・まとめて確かめる方法を決め、`plan` に項目ごとの確かめる環境（staging・本番）と担当（agent・human）か、対象外の理由を記録する。本番で確かめる項目は、[QAと証拠](qa.md)の「本番でも環境差と主要導線を確認する」を材料に選ぶ。理由付きの「なし」は、計画が無くても対象外として扱われる。項目を対象外にするのは、資料から理由が決まる場合（他の項目と重複する、開発中に確かめ済みなど）だけにし、確かめられないことを理由にしない（受入条件の変更に当たるので[停止と人への確認](workflow.md#失敗確認停止の共通ルール)に従う）。

未整理の項目は、ソースの差分と受入条件から補い、引継ぎを直して `sync` を起動するか、対象外の理由を記録する。開発Issueを特定できないPRによる未整理は、そのPRのタイトルか本文にIssueのキーを足して `sync` を起動する。利用者の判断が要る点だけを相談する。

### stagingの確認と記録

- 確認の前（特に人へ依頼する前）に、作業先の観測手段でstagingに今のheadが動いていることを確かめ、動いていなければ作業先の手順で配備する。同じソースの版でも配備し直すと観測される配備が変わり、`merge` は確かめた配備と違うとして拒否し、以前の記録とも配備がそろわなくなるので、確かめ直すか `carry` で今の配備へ持ち越す。記録の直前の照合は共通のCLIに任せる。
- 一つの操作で複数の項目を確かめたら、`record` にそのすべての項目を含め、証拠に操作を書く。不合格・未確認もそのとおりに記録する。
- 項目の結果は共通のCLIの記録をQAのコメントとし、証拠は[証拠の要件](qa.md#証拠の要件)に従う。項目の外で行う確認は[QAコメントの書式](qa.md#qaコメントの書式と更新)で書く。
- 人が確かめる項目は[Human QAの引き渡し](qa.md#human-qaの引き渡し)に従って依頼し、本人の報告から `--by human` で記録する。回答を待つ間も `staging_human_qa`・`production_human_qa` のままにする。
- 記録の後は `gate` を起動する。表示と記録が食い違っていたら、`sync` か `gate` を起動し直す。

### 追加のmerge

QAの途中でdevelopが進むと、`sync` が新しい出所の記録を追記する。`status` が示す以前のheadからの変更を読み、影響がある項目と影響を限定できない項目は確かめ直す。影響が無いと判断できる項目は、理由を付けて `carry` で持ち越す。毎回の全件の回帰や、製品の全テストは求めない。

### merge・配布・本番の確認

- `release-gate` が成功し、本文の必須のQAのうちstagingで行う確認が今のheadで合格したら、wrapperの `merge` を実行する。`merge` は判定とstagingで動いている配備を確かめ直し、そのheadを指定してmergeする。GitHubの画面や `gh pr merge` はstagingの配備を読み直さないので使わない。CIの必須の条件は作業先の資料とrulesetに従い、GitHubが拒否する条件を重ねて検査しない。
- 作業先の手順で配備・配布し（`release` スキル）、`record-deployment` で配布の事実を記録する。
- 本番の確認を `record --stage production` で記録し、`gate` を起動して表示を更新し、`status --stage production` で今の本番の版と照らす。

### Done

次がすべて成り立つときに、進行役がリリースIssueをDoneにする。

- 合意した配布先へ配布した。
- 本番で確かめると計画した項目が、今の本番の版で合格している。
- 項目の外で行う確認が合格している。
- 対象外の項目には理由がある。

### 次のリリースとの関係

mainへmergeした後のdevelopの変更は、次の release PR とリリースIssueへ集まる。進行中の本番の確認の対象を、黙って次の版へ変えない。未完了のまま次の版を配布するときは、両方のリリースIssueに未完了の項目・影響・移す先を記録する。不具合を修正版で直すときは、元のリリースの問題を修正版の確認へ結びつけ、元のリリースを未確認のままDoneにしない。

## 状態キーとの対応

| 工程 | 状態キー |
| --- | --- |
| 共通のCLIによる作成 | `todo` |
| 開始時の決定と計画、merge・配布 | `release` |
| stagingの確認 | `staging_agent_qa`・`staging_human_qa` |
| 本番の確認 | `production_agent_qa`・`production_human_qa` |
| 完了 | `done` |

専用のステータスが無い工程は[工程とステータス](workflow.md#工程とステータス)の規則に従う。`human_input` は外部の対応を待つときだけに使う。結果の語（合格・不合格・未確認・対象外）は[QAと証拠](qa.md)と同じ意味で使う。
