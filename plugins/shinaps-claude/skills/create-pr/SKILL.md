## 作業記録の保存先

作業記録はプロジェクトルートの `.shinaps/work/` 以下へ保存する。最初に記録を作るとき、`.shinaps/` を作成し、`.shinaps/.gitignore` がなければ内容 `*` と改行で作成する。既存ファイルは上書きせず、除外が不足する場合だけ `*` を追記する。ユーザーのグローバルignoreやルートの `.gitignore` の編集は不要。Git管理下では `git check-ignore` と `git status --short --untracked-files=all` で記録が未追跡変更に出ないことを確認する。既存の追跡済みファイルは自動で追跡解除しない。

既存の `.claude/shinaps/` 等の記録は渡されたパスから読み、無断で移動・削除しない。新規記録は新しい保存先を使う。共有する仕様書などを `docs/` 等へ出す場合は、明示された成果物の保存先に従う。秘密情報は記録しない。

# 変更をレビューできるPRにする

## プロジェクトの条件を読む

適用される `AGENTS.md`・`CLAUDE.md` と参照先、README、CI、既存スクリプトから、今回の対象・必須検証・禁止事項を確認する。現在の依頼と合意済みの条件を引き継ぎ、一般的な推奨をプロジェクトの必須条件に格上げしない。条件同士が矛盾し結果を左右する場合だけ一問ずつ確認する。任された実装判断は進める。

既存の情報から決まる内容を再質問しない。確認した新しい恒久方針は、ユーザーが保存を認めた場合だけプロジェクトの指示または参照先へ残す。スキル自身や他プロジェクトのルールへ書き込まない。

Linearの開発進行から受けた依頼では、[共通設定](../../references/linear/configuration.md)の合意済みの許可と[担当・工程](../../references/linear/workflow.md)を引き継ぐ。操作後は進行役へ結果を返し、[終了条件](../../references/linear/execution.md)に従って次工程を判断する。単独の依頼にはLinear進行や新しいゴールを必須にしない。

## 差分と宛先

プロジェクトルート、Git状態、remote、対象アカウント、base・headを確認する。ユーザーの指定を優先し、base未指定ならGitHubのdefault branchを取得する。比較には取得したリモートのbase refを使い、古いローカルブランチだけで判断しない。

対象ブランチの全コミット・baseとの全差分・未コミット差分を区別して読む。未コミット変更は自動でコミットせず、既存のコミット指示に従う。PR対象が不明な場合だけ一問確認する。既存PRがあれば重複作成せず、その状態を示す。更新を依頼されている場合は同じPRを更新する。

## タイトルと本文

リポジトリのテンプレート・言語・レビュー規約に従う。指定がなければ会話の言語で、具体的な問題と変更後の挙動を先に述べる。必要な設計判断、検証した内容と限界を添える。ファイル一覧の言い換え、作業日記、今回扱っていない別の論点を増やさない。見出しや敬体、日本語、文字数を全プロジェクトに強制しない。

## 作成と確認

- 完成したタイトルと本文を提示し、すでに許可された公開を進める。ドラフトの指定と対象ブランチを守る。
- 必要なpushは通常のpushを単独コマンドで行う。force-pushや履歴書き換えに広げない。
- 本文は一時ファイルに保存し、`gh pr create --base <base> --head <head> --title <title> --body-file <file>` で渡す。本文をシェルのコマンド置換に埋め込まない。
- 作成結果が不明な失敗は、再作成の前に同じheadのPRを読み戻す。URL、タイトル、base・head、draft状態を確認する。
- タスクへのPR添付ツールがある環境では作成したPRを添付し、URLを報告する。作成をマージ・デプロイまで拡大しない。
