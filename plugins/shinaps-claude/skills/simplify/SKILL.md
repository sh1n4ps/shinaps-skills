## 作業記録の保存先

作業記録はプロジェクトルートの `.shinaps/work/` 以下へ保存する。最初に記録を作るとき、`.shinaps/` を作成し、`.shinaps/.gitignore` がなければ内容 `*` と改行で作成する。既存ファイルは上書きせず、除外が不足する場合だけ `*` を追記する。ユーザーのグローバルignoreやルートの `.gitignore` の編集は不要。Git管理下では `git check-ignore` と `git status --short --untracked-files=all` で記録が未追跡変更に出ないことを確認する。既存の追跡済みファイルは自動で追跡解除しない。

既存の `.claude/shinaps/` 等の記録は渡されたパスから読み、無断で移動・削除しない。新規記録は新しい保存先を使う。共有する仕様書などを `docs/` 等へ出す場合は、明示された成果物の保存先に従う。秘密情報は記録しない。

# 目的から見直して減らす

## プロジェクトの条件を読む

適用される `AGENTS.md`・`CLAUDE.md` と参照先、README、CI、既存スクリプトから、今回の対象・必須検証・禁止事項を確認する。現在の依頼と合意済みの条件を引き継ぎ、一般的な推奨をプロジェクトの必須条件に格上げしない。条件同士が矛盾し結果を左右する場合だけ一問ずつ確認する。任された実装判断は進める。

既存の情報から決まる内容を再質問しない。確認した新しい恒久方針は、ユーザーが保存を認めた場合だけプロジェクトの指示または参照先へ残す。スキル自身や他プロジェクトのルールへ書き込まない。

## 担当とモード

- **「計画の簡素化」**: `shinaps-simplifier` (Opus / medium) 1体と新規Codex CLI (Astra / medium、fastなし) 1体。設計・プランレビューとは別の専任セッションを使い、[計画の簡素化](references/plan-simplification.md) の指示全文と同じ要件・目的・受入条件・最新計画・規約・調査結果を両者へ渡す。担当IDは1をOpus、2をCodexとする。コードの一般レビューは依頼しない。
- **それ以外（実装の簡素化）**: 新規Codex CLI 1体だけ。目的・外部契約・対象コード・最新計画・規約を渡す。[Codex CLI担当](../dev/references/codex-worker.md) のsimplify指示を使う。Opusの簡素化担当を追加しない。

Codexは共通CLI手順のモデル・effort・標準速度で起動する。計画モードのCLIには計画簡素化の指示を渡し、実装用の返却条件を混ぜない。全担当は読み取り専用で、他担当の今回の結果を読まない。完了まで計画・対象コードを変更しない。バッチ継続や修正計画の再確認は同じ担当を再開し、再開不能なら同じ役割へ確認済み・未確認範囲を引き継ぐ。

`dev` から「起動のみ」と指定された場合は担当をバックグラウンド起動し、担当名・エージェントIDまたはCLIセッションIDと実行ハンドル・対象範囲・未起動分を返す。メインが待機・全文保存・未完了分の再依頼を行い、全担当の結果をverifierへ渡す。ここでは結果を統合・選別せず、修正もしない。枠不足は順次実行し、起動済みを確認完了と報告しない。

起動のみでなければ全結果と確認範囲を待つ。失敗・未完了を指摘なしと扱わない。委託不可なら制約と独立確認未実施を報告する。「提案のみ」または「計画の簡素化」では、全提案・根拠・仕様変更の有無・未確認事項を返して終了する。devからの計画モードの提案は呼び出し元のverifierとarchitectが扱い、仕様変更はユーザー確認後に計画へ反映する。

単独の実装簡素化で適用も依頼されている場合だけ、以下へ進む。

## 判断と実行

- 目的、守る外部契約、現在の実装方法を区別する。今の構造を要件として正当化しない。
- 根拠の弱い前提、不要な分岐・互換層・重複、丸ごと消せる手順を実物から探す。削除 → 簡素化 → 最適化 → 自動化の順で考え、必要な段階だけ実施する。
- 利用箇所と契約を調べ、依頼範囲内で挙動を保つ削除を適用する。行数だけを減らして責務を混ぜない。仕様を変えることで簡単になる場合は、変わる挙動と推奨案を示して先に確認する。
- 変更の影響に合う検証を行う。問題がなければ変更を作らず終了する。
- 削ったもの、判断理由、確認結果を短く報告する。コミットや公開はこの工程の許可に含めない。
