# dev の工程（Managed Agents）

Claude Code の dev の工程を、Managed Agents のセッション向けに絞ったもの。役割・人数は初回メッセージの体制（[実装体制の判断](staffing.md)）の担当で進め（BASIC・ULTRAでは必須担当を下限に追加できる）、担当の委任・継続・作業先・出力は[起動手順](launch.md)に従う。

## 役割と継続

下の表は各役割の工程と継続を定める。起動する担当と人数は、受け取った体制の表（`staffing.md`）に従う。

| 工程 | 役割定義 | 継続と責任 |
| --- | --- | --- |
| Phase 3・4・6・7 | `shinaps-architect` | 担当1は設計・統合・設計適合性・指摘統合・修正計画を継続。担当2以降は独立設計と追加確認のみ |
| Phase 4 | `shinaps-plan-reviewer` | 修正版の再確認も同じ担当 |
| Phase 4・6 | `shinaps-simplifier` | 計画の簡素化は修正版の再確認も同じ担当。実装の簡素化は計画とは別の担当で、ラウンドと修正サイクルをまたいで継続 |
| Phase 4・6 | `shinaps-review-verifier` | 指摘検証担当を置く体制で、検証ラウンド（計画確認と実装後レビューの各ラウンドに1回）ごとに新規。今回の指摘を出した担当を流用しない |
| Phase 3・5・7 | `shinaps-implementer` | 1体。修正も同じ担当。設計担当を置かない体制（LITE）では、設計責任者として計画と指摘の整理・採否も担う |
| Phase 6 | `shinaps-reviewer` | 独立コードレビューは実装担当とは別で、レビューラウンドごとに新規。独立コードレビューを含む複数の種類を兼ねる場合は、独立コードレビューの規則に従う。可読性・慣習レビューを技術領域ごとに置く場合は、ラウンドと修正サイクルをまたいで継続し、技術領域が増えたら追加 |
| Phase 6 | `shinaps-refine-agent` | refine 担当を置く体制で、ラウンドと修正サイクルをまたいで継続 |

- 目的・範囲・規約全文・必読ファイル・今回の役割・担当番号・確認対象の版・成果物のパス・引き継ぎ先を依頼に渡す。実装担当にはファイルの所有範囲を明記する。
- 独立確認する担当には同じ版の入力を渡し、今回の他担当の結果を読ませない。対象を編集中にレビューせず、全結果が揃うまで lead と実装担当も対象を変えない。
- lead は体制と工程の調整、委任・待機・引き渡し、結果と未解決事項の取りまとめ、利用者判断の取り次ぎを行う。実装・修正、指摘の技術的検証と採否、設計適合性の実コード照合、既存の証拠がある検証の再実行は引き取らない。継続のターンで来る質問・修正も同じ分担で扱う。
- **修正サイクル**: 継続のターンで実装の修正が必要になったら、契機によらず、未対応の指摘の集合を一つの入力にして次の順に進める。
  1. 設計責任者が修正計画と、影響を受ける工程を決める。
  2. 設計・契約・検証条件を変える場合だけ、Phase 4 の扱いで再確認する。
  3. 同じ実装担当が修正する（Phase 5）。
  4. Phase 6 の担当（受け取った体制のとおり）と、指摘検証担当を置く体制ではその新規の担当が確認する。範囲は修正とその影響範囲とし、確定できなければ広げる。
  5. Phase 7 で統合・修正する。
- 起動失敗・空回答・未確認範囲を「指摘なし」にしない。

## Phase 1: タスクと体制

初回メッセージの必須入力が揃っていることを確かめ、目的・受入条件・範囲を確定する。作業先を[起動手順](launch.md)に従って用意し、関連コードと検証方法を必要な範囲だけ確認して、初回メッセージの体制の担当で進め、BASIC・ULTRAでは追加の担当を決め、作業記録に残す。

## Phase 2: 規約と必要な探索

規約の範囲は [SKILL.md の規約](../SKILL.md#規約)に従う。lead が読んで以降の担当へ全文を渡す。探索は各設計担当が自分の設計に必要な範囲で行う。

## Phase 3: 設計と計画

設計責任者は設計担当1、設計担当を置かない体制（LITE）では実装担当とする。計画には目的・不変条件・変更範囲（対象ファイルと責務）・実装順・検証を書く。設計担当が複数なら同じ入力で独立に検討させ、担当1が根拠で一つの案へ統合する。LITEでは実装担当が短い計画と検証方針を作り、報告の冒頭に書く。

## Phase 4: 計画の確認

計画レビュー・計画簡素化の担当へ同じ計画を渡し、指摘を「指摘の検証と統合」に従って扱う。LITEではこの工程を起動せず、計画はPhase 6の独立レビュー担当が、計画自体も誤りうる前提で確かめる。同じ対象について初回を1として最大2ラウンドとする。上限到達後に計画を修正した場合は、未再確認の変更と残課題を記録する。重大な設計リスク、仕様・許可の未決事項、必要な担当の未完了があれば Phase 5 へ進まず未完了で返す。

## Phase 5: 実装と検証

実装担当1体へ確定計画・必読ファイル・規約全文・所有ファイル・必要な検証を渡す。実装担当は計画を実装し、簡素化・セルフレビュー・必須検証を行う。実装ミスによる検証失敗の自己修正は3回まで。lead は報告の対象版・範囲・完了状態と、検証の証拠の所在・終了コードを照合する。全文の再レビューや同じ版の検証の再実行はせず、不足や矛盾は当該担当へ戻す。

## Phase 6: 実装後の確認

同じ差分を固定し、受け取った体制の担当と追加した担当を並行して委任する。技術領域ごとに可読性担当を置く場合は、全変更ファイルがちょうど1名の範囲に属することを確かめ、足りない技術領域があれば担当を足す。staged・unstaged・untracked を含めて対象を特定する。

- 設計適合性: 設計担当1（LITEでは独立レビュー担当）が計画・受入条件・責務・依存方向と実コードを照合する。
- 独立コードレビュー: 新規の `shinaps-reviewer`（独立コードレビュー）が、計画自体も誤りうるものとして正しさ・安全性・性能を確認する。
- 規約照合: refine 担当を置く体制では `shinaps-refine-agent` へ、規約（`AGENTS.md`・`CLAUDE.md` とその参照先）の全文を rule として、比較元からの差分コマンド（`git diff <比較元> -- <path>`）を変更範囲の確認コマンドとして渡す。未追跡の新規ファイルは全行を今回の変更として扱う。BASIC・LITEでは独立コードレビューの担当が、同じ規約全文で行う。
- 実装の簡素化: 実装の簡素化の `shinaps-simplifier`（LITEでは独立レビュー担当が兼ねる）が、目的・契約を保って削除・統合できる内容を確認する。
- 可読性・慣習: 体制の表の担当（ULTRAでは技術領域ごとの `shinaps-reviewer`（可読性・慣習レビュー）、BASIC・LITEでは独立コードレビューの担当が種類を複数指定されて兼ねる）へ、担当する範囲の差分と対象ファイルの現状全文、規約、計画に記した先例、合意済み仕様を渡す。

LITEでは、独立レビュー担当を両方の種類で委任し、設計適合性と簡素化もあわせて依頼する。

## 指摘の検証と統合（Phase 4・6）

指摘の整理は、設計責任者が採否を決める前に、指摘検証担当を置く体制では検証ラウンドごとに新規の `shinaps-review-verifier` が行い、いない体制では設計責任者が行う。全レポート・出典・確認範囲を使って全指摘の根拠・誤認・重複・対立・未確認を区別し、出典IDを保持して整理する。設計責任者がその結果から全項目の採否と理由、必要な修正と検証をまとめる。自分の成果物への指摘も根拠で採否を決め、その確認を独立検証とは報告しない。事実の食い違いや根拠不足で判断できない指摘だけ指摘元に確認する。指摘元への確認は同じ担当の継続で行い、レビューのラウンドに数えない。再現・検証が必要なら実装担当へ依頼する。仕様・受入条件の変更や許可範囲の拡大は利用者の合意前に採用しない。

## Phase 7〜8: 修正と終了判定

修正指示を同じ実装担当へ返す。実装後の全体レビューは、最初の dev と各修正サイクルのそれぞれで、初回を1として最大2ラウンド。同じサイクルの中の増員・交代・計画変更では上限をリセットしない。2回目の後に修正したら必要なテストを行い、最終差分が再レビューされていないことを報告する。重大な未解決事項、必須検証の失敗、必要な担当の未完了が残れば品質上の完了とは報告しない。

## Phase 9: コミット・push・draft PR と報告

1. コミット単位を依存順に確定する。stage は合意した範囲のパスだけにし、作業記録やその他のファイルを含めない。
2. 許可された場合だけ commit する。
3. 許可された場合だけ head ブランチへ push する。
4. 許可された場合だけ draft PR を作る。
5. [起動手順](launch.md)の出力を置き、状態行と SKILL.md の最終報告を書く。

許可されていない操作はその手前で止め、行わなかった操作を最終報告に書く。
