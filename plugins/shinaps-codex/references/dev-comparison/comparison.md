# 比較手順

## 1. 目的と範囲

[工程](workflow.md)を揃えたうえで、モデル・同じ役割の担当数・実行環境の差を比べる。採用する構成の決定と、既存 `dev` の切り替えはこの手順に含まない。

P1 は eafbbc5 の Claude 版 `dev` の割当を再現するが、比較専用の担当指示を使い、review / refine / simplify スキルを経由しないので、現行 `dev` の実行結果そのものではない。

## 2. 条件ファイルの事前固定

最初の実行の前に、比較セットのディレクトリへ `conditions.md` を保存し、ハッシュを記録する。以後は変更しない。

- 比較セットのディレクトリは、どの構成の作業環境にも含まれない場所に実施者が決める（例: 比較を管理するリポジトリの `.shinaps/work/comparisons/{ts}-{slug}/`）。回収先の `runs/<構成>/` も同じディレクトリに置く。
- 入口には条件ファイルを絶対パスで渡す。

`conditions.md` の様式:

```markdown
# 比較条件: <比較セット ID>

## 課題
- 課題ファイル: <パス>（要件・受入条件を含む）、sha256: <ハッシュ>
- 課題側のリポジトリと開始コミット: <リポジトリ> @ <コミット>
- 比較スキルの version: <plugin version>

## 規約スナップショット
- search_rules の結果: <ファイルのパス>、sha256: <ハッシュ>
- 適用する AGENTS.md / CLAUDE.md: <ファイルのパス>、sha256: <ハッシュ>（ファイルごと）
- 利用者のグローバル指示（Claude: `$CLAUDE_CONFIG_DIR/CLAUDE.md`、Codex: `$CODEX_HOME/AGENTS.md`。CLI が親・子へ自動で読み込む）: <ファイルのパス>、sha256: <ハッシュ>（無ければ「なし」）。両環境で内容が違う場合はその違いを書く

## 依存関係・データ
- <依存関係の導入状態、使うデータとその取得方法>

## 探索条件
- 探索担当数: <数>
- 範囲分割: <なし／分割する範囲>
- 既存調査の再利用: <可／不可。可ならその成果物のパス>

## 事前の合格条件
- 受入条件: <課題ファイルの節、または全文>
- 必須の検証コマンド: <コマンド>
- 評価項目と基準: <項目ごとの基準>

## 許可範囲
- <変更してよい範囲、外部への書き込みの可否、コミットしないこと>

## 実行権限
- Claude: <実施者が既に許可した permission mode>
- Codex: <実施者が既に許可した sandbox と承認>
- 権限機構の違い: Claude の担当は親の権限で動き、Codex は担当ごとに sandbox を持つ。<この違いで変わる点>
- 必須の検証コマンドをこの権限の範囲で両環境で実行できるかの確認結果: <日時、コマンド、結果>

## 終了条件
- <工程の終了条件に加える条件があれば記載>

## 実行する構成と順序
- <例: P1 → P3 → P5>

## 各構成の親の起動コマンド
| 構成 | 起動コマンド（構成表の写しに実行権限を入れたもの） |
|---|---|
| P1 | <コマンド> |
```

必須の検証を実行できない環境があれば、権限を広げずにその旨を記録し、比較を行うかを実施者が判断する。

## 3. 独立した作業環境

- 構成ごとに、開始コミットから作った別の作業環境（worktree またはクローン。対象リポジトリの方針に従い、worktree を作らない環境ではクローンを使う）と別ブランチ、新しい親セッションを使う。
- 作業環境は実施者が事前の許可のもとで作る。入口は作らない。
- 同じ担当の再開だけが同じ作業環境を使う。
- 他の構成のコード・計画・レビュー・会話を渡さない。
- 構成間は直列に実行する。
- 作業環境のディレクトリ名は、英数字以外の文字だけが異なる名前にしない（[実行記録](record.md)の親の特定に使うため）。

## 4. 自動メモリ

比較セットの開始前に、`$CLAUDE_CONFIG_DIR`（未指定なら `~/.claude`）の `projects/` 配下の、課題リポジトリに対応する memory ディレクトリと、`$CODEX_HOME`（未指定なら `~/.codex`）直下の `memories` で始まるエントリすべて（ディレクトリと sqlite ファイル）の内容のハッシュを記録する。各実行の後に再計算し、変化があれば `run-record.md` と比較記録に書き、次の実行の前に実施者が扱いを判断する。メモリ機能の設定は変更しない。

## 5. 実行

条件ファイルの起動コマンドで親セッションを開始し、入口に担当数と条件ファイルの絶対パスを渡す。人の介入は全件を `run-record.md` に記録する。

## 6. 回収

各実行の後、次のものを比較セットの `runs/<構成>/` に保存する。回収のためにステージ・コミットはしない。

- `run-record.md`
- 追跡ファイルの差分（`git diff <開始コミット>`）
- 未追跡ファイル（`git ls-files --others --exclude-standard`。`.shinaps/` と秘密情報を除く）の一覧と内容
- 検証結果とレポート

## 7. 匿名化評価

全実行の後、成果物とレポートから構成名・モデル名・識別できるパスを伏せて無作為な記号を付ける。対応表は実施者だけが別ファイルで持つ。評価者（人、またはどの実行にも関わっていない新しいセッション）が事前の合格条件で評価し、結果を確定してから対応表を開く。

## 8. 比較記録

構成ごとに次を表にする。

- 合格条件の結果
- 時間
- 使用量（実測／推定／取得不可）
- 修正回数
- 人の介入
- 設定の判定
- 割当外の依頼の確認結果
- 自動メモリの差分
- 2体目の発見の分類

判定が「観測できる設定は一致（指定のみの項目あり）」だけの実行以外は、比較データとして扱わず、その判定を書く。指定のみの項目（[構成表](configurations.md#観測手段の無い項目)）は全構成について併記する。tier の実際の利用を確認できない構成の速度差は、tier まで揃えた結果とは書かない。

## 9. SHINAPS-98 の初回

P1 → P3 → P5 を直列に実行し、結果の検討で止まる。P2・P4・P6・P7 は候補として記載し、自動では実行しない。
