# dev の工程

Claude Codeのdev（`dev-claude`）の工程。メインが調査・設計・実装・検証・修正・指摘の採否を行い、[実装体制の判断](staffing.md)で選んだ体制の担当が独立した別案と独立確認を行う（BASIC・ULTRAでは必須担当を下限に追加できる）。担当の起動・継続は[起動手順](launch.md)に従う。

## 1. 前提と作業記録

適用される `AGENTS.md`・`CLAUDE.md` と参照先、CI、既存スクリプトから作業条件を読み、依頼・範囲・制約を引き継ぐ（[依頼範囲と操作](../request-scope.md)）。仕様を左右する不足だけ一問ずつ確認する。新しい恒久方針は了承を得て保存する。利用できないツールを仮定しない。

devの依頼は登録済みのdev役割への委託（Agentでの起動）を含む。委託しないのは、利用者または作業先の制約が委託を禁止した場合と、実行環境が委託を拒否した場合だけで、その扱いは[体制](staffing.md)の「維持する条件」に従う。worktreeは依頼範囲の中で隔離が必要な場合に使う。サービス規約を取得できない工程は未照合と明示する。

作業記録は `.shinaps/work/{YYYYMMDD-HHMMSS}-{slug}/` と `raw/` へ保存し、[共通手順](../work-records.md)に従って保全する。担当の応答は全文を参照できる形で保存し、対象版・役割・担当ID・確認範囲・完了状態を対応づける。短い作業は短い計画・記録にする。

## 2. 役割と継続

下の表は各役割の工程と継続を定める。起動する担当と人数は、選んだ体制の表（`staffing.md`）に従う。

| 工程 | 役割定義 | 継続と責任 |
| --- | --- | --- |
| Phase 2 | `shinaps-explorer` | 任意。互いに独立した領域を並行して調べるときに、領域ごとに起動 |
| Phase 3 | `shinaps-architect` | 独立設計担当を置く場合（ULTRAでは必須、BASICでは追加できる）。独立案と、その案への追加の質問への回答だけを担う |
| Phase 4 | `shinaps-plan-reviewer` | 計画レビューと計画の簡素化をあわせて見る。修正版の再確認も同じ担当 |
| Phase 6 | `shinaps-reviewer` | 独立コードレビューを含む担当はレビューラウンドごとに新規。規約照合と可読性・慣習レビューを技術領域ごとに置く担当は、ラウンドと修正サイクルをまたいで継続し、技術領域が増えたら追加 |

- 異なる役割と独立比較の担当は別コンテキストで起動する。担当番号を起動前に固定し、同じ役割の継続は同じIDを使う。再開できない場合（resumeをまたぐ場合を含む）は同じ役割へ既存の成果・最新の差分・未解決点を引き継いで交代を記録する。
- 目的・範囲・規約全文（Phase 6の照合では読むファイルの指定）・必読ファイル・今回の役割・担当番号・確認対象の版・依頼するレビューの種類を依頼に渡す（独立設計担当への依頼はPhase 3に従う）。担当は読み取り専用で、自分でエージェントを起動しない。
- 計画の確認と実装後の確認に、[レビューの共通契約](../review.md)の「対象の固定」「独立性」「完了の判定」を適用する。計画の確認では対象の版を計画の内容のハッシュとし、差分・機械検査・変更範囲の文は適用しない。Phase 4 の入力として定めた両案は他担当の結果に当たらない。独立案（Phase 3）はPhase 3の節に従う。継続担当には前回の確定済み指摘と採否を渡してよい。
- メインは、依頼の確認、体制と工程の調整、調査・設計・計画の統合・実装・検証・修正、指摘の検証と採否、修正計画、担当の起動・待機・全文保存、結果と未解決事項の取りまとめ、利用者判断の取り次ぎを行う。体制が求める独立確認（独立案・計画の独立確認・実装後の独立レビュー）をメインの自己確認で代えない。
- devの完了後に同じ会話・sessionで来る依頼（対話の次のターン、resume、Bridge、人の相談、QA差し戻し）も同じdevとして扱う。ただし、利用者が `review` を明示して起動したレビューはdevの工程とは別の作業とし、devの体制とレビューの回数を引き継がない。その結果の修正を依頼された場合は人の修正開始として修正サイクルに入る。質問への回答と人の指摘の調査は、メインが読み取りだけで行い、編集は修正サイクルで行う。初回devの完了・短い追加依頼・通常の会話への復帰を例外にしない。Codexが[UIの微調整](../linear/workflow.md#codexによるuiの微調整)で返した差分は、メインが取り込み、現在の工程の差分として検証し、既存のレビューを続ける（回数はリセットしない）。
- **修正サイクル**: devの完了後に実装の修正が必要になったら（人の修正開始（[人のレビュー](../human-review.md)）、Codex QAの差し戻し、コミット中の指摘など、契機によらず）、未対応の指摘の集合を一つの入力にして次の順に進める。人の修正開始では、体制を[体制の選択](staffing.md)に従って確認する。入力が一致する結果は[テスト方針](../testing.md)に従って引き継ぐ。一部をコミットした後の修正は `commit` の規定どおり後続単位にする。
  1. メインが修正計画と、影響を受ける工程を決める。
  2. 設計・契約・検証条件を変える場合だけ、Phase 4の扱いで再確認する。
  3. メインが修正する（Phase 5）。
  4. Phase 6の担当（選んだ体制のとおり）が確認する。範囲は修正とその影響範囲とし、確定できなければ広げる。
  5. Phase 7で統合・修正する。

## 3. Phase 1: タスクと体制の確定

依頼に「規約の適用結果を記録しない」があれば、この時点で[作業記録へ書く](../rules.md#適用結果を記録する)。

依頼・引数・指定された成果物から目的・受入条件・範囲を確定する。確定済みの内容を聞き直さず、依頼されていない過去の作業を始めない。成果物に実装可否の状態があればreadyを確認し、欠落・不明なら変更内容を推測せずタスクを確定する。内容ハッシュがある根拠は現在値と照合し、古い根拠は読み直す。

Issue・既存spec・調査記録・関連コード・検証方法を必要な範囲だけ確認する。依頼に書かれた体制（無ければ[体制の選択](staffing.md)に従って確認する）の担当で進め、BASIC・ULTRAではlinear-executeから受けた材料と現物からメインが追加の担当を決める。設計を始める前に、[体制](staffing.md)の「記録と引き渡し」の項目を作業記録の `staffing.md` へ保存し、短く報告する。不足する調査があればPhase 2で補い、体制を更新する。

## 4. Phase 2: 規約と必要な探索

規約はメインが取得する。担当はShinaps MCPを呼ばない。Phase 3・4の担当へは全文を渡し、Phase 6の照合の担当へは[snapshot](../rules.md#照合のために取得する)を読ませる。

- [Shinaps規約の取得](../rules.md)に従い、対象に関連するfacetで一覧を取り、必要な全文を取得する。
- プロジェクト規約と関連docs、引き継いだ調査の必読ファイルを確認する。時間に依存する根拠が判断に影響する場合は公式情報で確かめる。
- 調査はメインが行う。BASIC・ULTRAでは、互いに独立した領域を並行して調べる場合に探索担当を置ける（任意）。探索担当には既存成果物と不足する問いを渡し、`raw/explorer-{n}.md` に結果を保存する。

新しい不確実性・影響範囲が見つかったら、設計前に体制を更新する。

## 5. Phase 3: 設計と計画

メインは設計を始める前に[設計の観点](design.md)を読み、その観点と書式で計画を作る。LITEでは短い計画と検証方針にする。計画は `plan.md` に書き、Phase 4が終わるまで「未確定」と明記する。

独立設計担当を置く場合は、次の性質を保つ。

- 独立設計担当への依頼（追加の質問を含む）には、要件・制約・規約全文・引き継いだ成果物だけを入れ、メインの案・結論・探索の結果は入れない。
- メインは独立案を読む前に自案を `raw/design-main.md` に保存し、保存後は変えない。Claude Codeでは担当の結果の全文がメインに届き、届いた時点でメインは独立案を読むことになるので、自案を保存してから独立設計担当を起動する。
- 独立案は `raw/architect-{n}.md` に保存する。メインが両案を根拠とトレードオフで比べて一つの計画にまとめ、`plan.md` に書く。比較の節には論点ごとの採否と理由を書く。

## 6. Phase 4: 計画の確認

計画レビュー担当を起動し、同じ計画・要件・調査・規約を渡す。計画レビューと計画の簡素化をあわせて依頼する。独立設計担当を置いた場合は、統合計画・両案（`raw/design-main.md` と独立案）・比較の節を渡し、独立案の論点を根拠なく退けていないかも確かめさせる。LITEではこの工程を起動せず、計画はPhase 6の独立コードレビューの担当が、計画自体も誤りうる前提で確かめる。

全結果を `raw/plan-review-{round}-{n}.md` に保存し、「指摘の検証と統合」に従う。計画変更があれば `raw/plan-revised-{round}.md` に残し、変更の影響を受ける担当へ同じ修正版と前回の採否を渡し、修正箇所と影響範囲を中心に再確認させる。影響範囲を確定できなければ再確認の範囲を広げる。契約・設計・検証条件に影響しない表記整理だけで新たなラウンドを作らない。

採用すべき指摘と必要な判断が解決したら `plan.md` を確定し、「未確定」の表示を外す。計画段階には回数上限を設けないが、目的のない反復や新しい根拠のない却下案の再提案は行わない。runtime固有の上限があれば起動手順に従い、未確認の最終変更と残課題を明示する。

## 7. Phase 5: 実装と検証

メインは `plan.md` を再読し、計画を実装する。

- 実装前に、規約と、計画に記した同種の既存実装2つを確認する（計画に無ければ選んで記す）。対象ファイルの現在の内容を読んでから編集する。
- 同じ作業ツリーでは他者も作業している。既存の変更を戻さず、現在の内容に合わせる。
- 計画で決めた最終構造を実装する。必要な移動・分割を差分削減のために省略せず、全利用側の参照更新・旧経路や重複の解消・既存利用側の回帰確認まで行う。
- 目的・仕様・受入条件の変更が必要と分かったら、該当作業を止めて人に確認する。計画の前提が成立しない技術的な矛盾は計画を直し、設計・契約・検証条件が変わればPhase 4の扱いで再確認する。通常の判断は既存の合意と規約で解決する。
- 検証やレビューの指摘には原因を確認して対処する。期待値や受入条件を弱めて成功扱いにしない。
- 実装後、目的を保ったまま削除・統合できる処理を確かめ、不要な分岐・重複・互換層を減らしてからセルフレビューする。
- [テスト方針](../testing.md)に沿って、プロジェクトの規約・CI・変更の影響に応じた検証を行う。検証でSimulator等の仮想端末を使う場合は、[QAと証拠](../linear/qa.md) の「Simulatorの所有と再利用」に従う。
- Claude CodeでiOSの不具合の再現や原因の調査に実際の画面・操作の観測が必要な場合は、Apple公式のXcodeプラグインの `device-interaction` スキルを使える。使うのはこの目的の場合だけとし、同スキルがUI変更後の毎回の確認を勧めていても実装後の一律確認には使わない（動作QAは[QAと証拠](../linear/qa.md)の工程が担う）。操作とセッションの手順は同スキルに従う。端末は上の「Simulatorの所有と再利用」に従ってUDIDで指定し、同スキルのツールは指定に近い端末を選ぶことがあるため、開始したセッションの端末がそのUDIDと一致することを確かめる。未導入・未承認・その端末を選べない・一致しないなど使えない場合は、導入や権限の変更を手順に加えず、観測していない内容を未確認として扱う。観測は対象版・端末と合わせて `implementation.md`（Phase 7と修正サイクルでは `fix-log.md`）に残し、検証やQAの合格に読み替えない。
- 実装ミスによる検証失敗の自己修正は3回まで。超えた場合は根拠と未解決点を記録し、追加試行・差分のレビュー・計画への差し戻しの選択肢を人に確認する。

メインは `implementation.md` に、変更ファイルと変更内容、設計理由、確認した先例と慣習から外れる判断の理由、簡素化した点、計画からの変更と合意、検証コマンドと終了コード・証拠の所在、未実施事項・未解決点を書く。実行していない検証を成功と書かない。UIレビューはこの工程に含めず、linear-executeのAgent QA等で扱う。

## 8. Phase 6: 実装後の確認

[レビューの共通契約](../review.md)に従い、同じ差分を固定して、選んだ体制の担当と追加した担当を並行して起動する。設計適合性は、独立コードレビューの種類の中で毎回依頼する。変更範囲の確認コマンドは `git diff HEAD -- <path>` を渡す。

固定した対象について、[Shinaps規約の取得](../rules.md)の「照合のために取得する」で領域ごとに snapshot を作る。`checks` があれば、担当へ渡す前に[規約の機械検査](../lint.md)の「照合で使う」を行い、「担当へ渡す」の依頼文で読ませる。

結果を `review-{round}-{n}.md` に保存する。未照合の規約はPhase 9に報告する。

## 9. 指摘の検証と統合（Phase 4・6共通）

[レビューの共通契約](../review.md)の「指摘の検証と統合」に従う。全項目の採否と理由、必要な計画修正・実装修正・検証は、Phase 4は `plan.md`、Phase 6は `fix-log.md` の「指摘の採否」の節に書く（`fix-log.md` ではQAの変更記録と節を分ける）。仕様を変えなければ解消できない欠陥は、Phase 5 の「該当作業を止めて人に確認する」に回す。複雑な対立は[体制](staffing.md)の「途中の増員」で担当を追加できる（LITEでは体制の変更を相談する）。

## 10. Phase 7〜8: 修正と終了判定

メインが採否に従って修正し、変更と必要な検証を `fix-log.md` に記録する。Local Agent QAの後の修正では、[変更記録](../linear/qa.md#qaの時点対象最終qa)の項目も残す。修正不要ならPhase 9へ進む。

実装後の全体レビューは、最初のdevと各修正サイクルのそれぞれで、初回を1として最大2ラウンド。同じサイクルの中の増員・交代・計画変更では上限をリセットしない。1回目の後に修正したら、同じ最新差分でPhase 6の体制に必要な増員を加えて2回目を行い、検証・統合する。2回目は修正箇所と影響範囲を中心に確認し、影響範囲を確定できなければ確認範囲を広げる。範囲を絞った場合も必須検証は全体で実行し、完了前にメインが全差分を計画・受入条件と照合する。2回目の後に修正したら必要なテストを行い、3回目の全体レビューは起動せず、最終差分が再レビューされていないことを報告する。

重大な未解決事項、必須検証の失敗、必要な担当の未完了が残れば品質上の完了とは報告しない。

## 11. Phase 9: 完了と引き渡し

全指摘の採否が確定したら、[規約の適用結果](../rules.md#適用結果を記録する)を既定で記録する（作業ごとにOFFにできる。失敗は未記録として報告し、完了の判定を変えない）。

選んだ体制・追加した担当と変更理由、実際の担当・確認範囲と必須担当の完了状況（合意による未実施を含む）、計画と実装後のレビュー回数、採否・修正（退けた Critical・Warning と、欠陥を示す Info・提案の件数と根拠の場所、人の判断で解決した件数と判断の記録の場所、既存箇所の指摘の件数を含む）、検証結果、未実施・未照合・未解決事項を報告する。機械検査の組の状態ごとの数と実行できなかった理由、`rule-coverage` の未確認の規約・ファイル、規約照合の種類を依頼しない体制（BASIC・LITE）では規約を独立コードレビューの中で照らしファイルごとの完了一覧が無いことも書く。修正サイクルの後は、初回の報告項目を最新にし、対応した指摘と採否・再実施した工程・[変更記録](../linear/qa.md#qaの時点対象最終qa)を加える。

linear-executeから受けた作業は未コミットの差分と結果を進行役へ返す。devの完了はLocal Agent QAへの引き渡しであり、進行全体の終了ではない。[Linear共通設定](../linear/configuration.md)と[担当と工程](../linear/workflow.md)に従い、autoはQA後の差分確定の依頼を受けて、manualは人のコミット開始依頼で `commit` を始め、単位の退避・stage・commitはQA結果の引き渡し後に行う。auto経路は [Claude CLI](../linear/claude-cli.md) のresultへ報告し、同じsessionのresumeで質問・修正を受ける。manual経路は同じ対話セッションで人と作業し、[Bridge](../linear/bridge.md)で依頼元Codexへ報告する。manualの完了時は、修正サイクルの後も含めて、人へユーザーのレビュー待ちと明示する（[manualの手順](../human-review.md)）。

単独のdevではコミットが依頼の到達点に含まれる場合だけ範囲とモードを `commit` へ渡す。含まれなければ未コミットで返し、形式的な確認を追加しない。PR・リリースも依頼の到達点に含まれる範囲で各スキルへ渡す。単独devにLinear進行・新しいゴールを必須にしない。

explore・spec・review・debugからの成果物は入口の引数で直接渡す。reviewから渡された指摘は修正サイクルの入力とし、体制が渡された場合はその体制で進める。専用の引き継ぎファイルは作らず、Phase 1・2で既存成果物を再利用する。
