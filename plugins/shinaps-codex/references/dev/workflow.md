# dev の工程

dev の入口（Claude 版 `dev-claude`・`dev-claude-ultra`、Codex 版 `dev-codex`・`dev-codex-ultra`）が共有する工程。入口は同じ役割の担当数（1体／2体）だけを決める。担当の起動・継続と使うツールは、同じディレクトリの[起動手順](launch.md)に従う。

## 1. 前提

### 作業記録の保存先

作業記録はプロジェクトルートの `.shinaps/work/` 以下へ保存する。最初に記録を作るとき、`.shinaps/` を作成し、`.shinaps/.gitignore` がなければ内容 `*` と改行で作成する。既存ファイルは上書きせず、除外が不足する場合だけ `*` を追記する。ユーザーのグローバルignoreやルートの `.gitignore` の編集は不要。Git管理下では `git check-ignore` と `git status --short --untracked-files=all` で記録が未追跡変更に出ないことを確認する。既存の追跡済みファイルは自動で追跡解除しない。

既存の `.claude/shinaps/` 等の記録は渡されたパスから読み、無断で移動・削除しない。新規記録は新しい保存先を使う。共有する仕様書などを `docs/` 等へ出す場合は、明示された成果物の保存先に従う。秘密情報は記録しない。

### プロジェクト条件

この節は以下の工程全体に適用する。適用される `AGENTS.md`・`CLAUDE.md` と参照先、CI、既存スクリプトから今回の条件を読み、明示された依頼・許可を引き継ぐ。仕様に影響する不足だけ一問ずつ確認する。新しい恒久方針の保存はユーザーの了承を得てプロジェクト側へ行う。

質問は現在のセッションで利用できる質問の手段を使い、一問ずつ確認して回答を待つ。現在のセッションで提供されていないツールは仮定しない。

### 委託と規約照合

別セッションへの委託・新しいworktreeは明示された許可がある場合だけ行う。委託不可なら現在のセッションで調査・計画・レビューの観点を順に確認し、独立レビューとは報告しない。このときテストの判断は[テスト方針](../testing.md)に従う。独立レビューがプロジェクトの必須条件なら未完了として扱う。Shinapsのエージェント名は各 runtime の plugin で公開された名前を使う。サービスのrule照合が必要な工程でMCPを利用できなければ、その工程を未確認として報告し、照合済みとしない。

## 2. 役割と継続の規則

| Phase | 役割 | 担当数 | 継続／新規 | 役割定義 |
|---|---|---|---|---|
| 2 | 探索 | 1（領域が広ければ範囲を分けて並列） | 新規 | `shinaps-explorer` |
| 3 | 設計担当1（設計案統合・プラン統合・設計適合性・指摘統合） | 1 | 全工程で継続 | `shinaps-architect` |
| 3 | 設計担当2 | 1体: なし／2体: あり | 設計の追加確認だけ継続。他の役割へ流用しない | `shinaps-architect` |
| 4 | 計画レビュー担当1 | 1 | 修正版の再確認で継続 | `shinaps-plan-reviewer` |
| 4 | 計画レビュー担当2 | 1体: なし／2体: あり | 同上 | `shinaps-plan-reviewer` |
| 4 | 計画簡素化担当1 | 1 | 同上 | `shinaps-simplifier`（計画の簡素化） |
| 4 | 計画簡素化担当2 | 1体: なし／2体: あり | 同上 | `shinaps-simplifier`（計画の簡素化） |
| 4, 6 | 指摘検証（verifier） | 1 | 検証ラウンドごとに新規 | `shinaps-review-verifier` |
| 5, 7 | 実装 | 1（複製しない） | 修正で継続 | `shinaps-implementer` |
| 6 | 設計適合性 | 1（設計担当1 を再開） | 継続 | `shinaps-architect` |
| 6 | 独立コードレビュー | 1 | ラウンドごとに新規 | `shinaps-reviewer` |
| 6 | refine | 1 | 同一ラウンドのバッチは継続 | `shinaps-refine-agent` |
| 6 | 実装の簡素化 | 1 | ラウンドごとに新規 | `shinaps-simplifier`（実装の簡素化） |

- 担当は[起動手順](launch.md)に従って起動し、今回の入力（役割名・担当番号・ラウンド・担当数と、各 Phase が定める渡す情報）を依頼の本文で渡す。担当番号は起動前に固定する。読む資料はパスで指定し、作業記録にある他の担当の成果物は、工程が渡すと定めたもの以外を読ませない。担当には、他のエージェントを起動しないこと、実装担当以外はファイルを変更しないことを伝える。
- 異なる役割は、同じモデルでも別のコンテキストで起動する。同じ役割の継続は同じ ID を再開する。再開できなければ同じ役割の新しい担当へ確認済み・未確認の範囲と最新の文脈を引き継ぎ、交代を報告に残す。
- 設計担当2 を他の役割へ流用しない。設計担当1 は設計から指摘統合まで同じ ID で続ける。
- 独立に確認する担当（設計担当、計画レビュー担当、計画簡素化担当、実装後の4役割）は、今回の他担当の結果を受け取らず、意見を交換しない。全担当の完了まで計画・対象コードを変更しない。
- メインは担当の起動・待機・全文保存・受け渡し・ユーザーへの確認と、各 Phase が定める作業を行う。担当の判断を代わりに行わず、指摘を先に選別・要約・重複整理せず、検証をやり直さない。担当は自分で他の担当やエージェントを起動しない。
- 並行して起動する担当が同時実行の上限を超える場合は、[起動手順](launch.md)のとおり分けて起動する。分けても、担当の数・独立性・渡す情報は変えない。

## 3. 担当数の設定

担当数の設定（1体／2体）が作用するのは、独立設計（Phase 3）・計画レビュー（Phase 4）・計画簡素化（Phase 4）の 3 か所の担当2 の有無だけである。1体の設定では担当2 を起動しない。実装担当は常に 1 体で、修正も同じ担当が行う。設計適合性・独立コードレビュー・refine・実装の簡素化・verifier を含む、それ以外の工程・役割・成果物・終了条件は担当数で変わらない。

## 4. 実行フロー

### Phase 1: タスクの確定

1. 今回の明示的な依頼・引数・指定された引き継ぎ資料からタスクを確定する。どれかで確定していれば、形式的な引数の再入力を求めずに進める。確定できないときだけ一問確認し、過去の文脈から依頼されていない作業を始めない。作業範囲・許可は広げない。
2. 依頼や引数に成果物のパス（旧 `.claude/shinaps/` を含む）があれば読み、タスク・確定事項・未解決点を取り込む。
   - 成果物に実装可否の状態（例: 実装 handoff の status）があれば ready であることを確認する。欠落・不明・ready 以外なら変更内容を推測せず、元の調査に戻るか、実装内容をここで確定するかを確認する。
   - 根拠ファイルの内容ハッシュの記録があれば現在値と照合する。不一致・欠落の根拠は古いとみなし、同じパスを読み直して結論を確かめ直す。ブランチ・HEAD・作業ツリーの状態が同じでも照合を省かない。
   - 同じディレクトリの調査記録（`raw/` 配下）は Phase 2 で再利用する。
3. 今回の依頼に関連する既存の spec・調査レポート・Git の変更履歴を確認し、引き継ぐ決定と根拠を要約する。既存成果物がなければ追加取得は不要。
4. タスクから英語 slug（kebab-case、30 文字以内）を作り、作業ディレクトリ `.shinaps/work/{YYYYMMDD-HHMMSS}-{slug}/` と `raw/` を作る。
5. タスクの文面が曖昧、または制約が不明確な場合は一問ずつ確認する。

### Phase 2: 規約の取得とコードベース探索

規約はメインが取得し、以降の担当へ全文を渡す。担当は shinaps MCP を呼ばない。

- `list_search_facets` で facet を確認し、`search_rules` に対象リポジトリの repoOwner・repoName と、対象ファイルから推定した facet を渡して userRules・officialRules の全文を得る。
- facet の取得結果にあるバージョンの対象と manifest・lockfile 等を照合し、確認できたバージョンだけを `projectVersions` に指定する。確認できない対象は、共通ルールだけの照合になったと記録する。
- 関連する `AGENTS.md`・`CLAUDE.md` と、それが正本として参照する docs のうち今回の領域に関係するものを読む。

引き継ぎ成果物がある場合は、Phase 1 で読んだ成果物と同じディレクトリの調査記録を現在の実装を理解する証拠として再利用し、必読ファイルをメインが直接読む。時間に依存する外部の根拠（現行仕様・バージョンなど）は、実装判断を左右する場合に公式情報で確かめ直す。情報が十分かつ最新なら `shinaps-explorer` を起動しない。情報不足・陳腐化・実装範囲の追加がある場合だけ補完として起動し、`raw/explorer-supplement.md` に保存する。

引き継ぎがない、または事前調査が不足する場合は `shinaps-explorer` を起動する（領域が広ければ範囲を分けて並列）。タスク、Phase 1 の既存成果物の要約、探索の狙いを渡す。記録先は `raw/explorer.md`（並列時は `raw/explorer-{n}.md`）。

### Phase 3: 実装ブループリント策定

設計担当1 と、2体の設定なら設計担当2 を、同じ入力で並行して起動する。互いの案や今回の他担当のレポートを読ませず、読み取り専用で独立に設計させる。

渡す情報:

- タスクの目的・受入条件・合意済みの制約
- Phase 2 の調査結果・必読ファイル・根拠
- Phase 2 で取得した規約全文と、適用される `CLAUDE.md`・`AGENTS.md`
- 既存配置を前提にせず、変更後の責務の所有者・配置・依存方向を先に決めること。必要な移動・分割・置き換えは変更量が大きくても含め、最小化するのは到達に不要な変更とする
- 利用範囲が変わる責務の配置判断（移動／維持の理由）・外部契約・データフロー・全利用側の更新・実装順・回帰検証を、根拠付きの一つの推奨案として返すこと
- コード編集・追加委託・shinaps MCP の直接呼び出しは禁止

2体の設定では、設計担当1 の案を `raw/architect-1.md`、設計担当2 の案を `raw/architect-2.md` に保存する。

- 2体の設定: 両方の結果が揃ったら設計担当1 を「設計案統合」として再開し、両案の根拠・トレードオフを比較して一つの計画を返させ、`raw/architect.md` に保存する。多数決や単純な継ぎ合わせにせず、採否と理由を残す。設計者間の反復議論は追加しない。
- 1体の設定: 設計担当1 の案を統合済みの計画とし、`raw/architect.md` に保存する。

この計画を Phase 4 のレビュー対象にする。設計担当2 は設計上の追加確認が必要な場合だけ再開し、独立コードレビューなど他の役割へ流用しない。起動失敗や未完了を設計済みと扱わない。

### Phase 4: プランレビューと計画の簡素化

計画レビュー担当と計画簡素化担当（それぞれ担当1、2体の設定なら担当2 も）を、同じ計画で並行して起動する。

計画レビュー担当へ渡す情報:

- タスクの目的・受入条件、Phase 2 の調査結果と規約全文
- Phase 3 の計画全文（再策定時は最新案）
- 「設計・要件・実装可能性・リスク・テスト戦略をレビューし、判定と具体的な修正案を返す。他のプランレビュー担当の結果は読まず、意見を交換しない」

計画簡素化担当へは、今回の目的・受入条件・最新計画・規約・調査結果・成果物パスを渡し、「計画の簡素化」として、仕様・状態・操作・実装方針から減らせるものだけを検討させる。

全担当へ同じ計画を渡し、他担当の今回の結果は読ませない。全担当の完了まで計画を変更しない。メインは `raw/plan-review-{round}-{n}.md` / `raw/plan-simplify-{round}-{n}.md` に全文保存する（round は 1 始まり、n は担当番号）。未完了は同じ担当へ戻す。

全結果が揃ったら、新しい verifier を起動して全結果を渡す（渡す内容は「指摘の検証」の節）。検証結果を `raw/plan-verification-{round}.md` に保存し、設計担当1 を「プラン統合」として再開する。設計担当1 は検証結果の全項目の採否・根拠と計画の修正案を返す。簡素化で機能・ユーザー体験・外部契約・受入条件が変わる提案は、変更点・失うもの・期待効果を示してメインからユーザーに確認する。承認前に計画へ採用しない。

計画を変更する場合は設計担当1 が修正版を返し、メインが `raw/architect-revised-{round}.md` に保存する。同じ計画レビュー担当と計画簡素化担当へ同じ修正版・承認済み変更・前回の採否を渡し、再確認 → 新しい verifier → 設計担当1 を繰り返す。担当を再開できなければ同じ役割の担当へ引き継ぐ。他担当の今回の未確定結果は共有しない。

計画段階には回数上限を設けない。修正不要で、採用すべき指摘と必要な判断・確認が解決したら `plan.md` を確定し、Phase 5 へ進む。回数を埋める再確認や、新しい根拠のない却下案の再提案は行わない。委託不可なら制約と独立確認の未実施を明記する。

計画段階では refine を行わない。設計に関わる規約はプランレビューで確認し、コードの規約照合は実装後に行う。

### Phase 5: 実装

#### A. 引き継ぎ

メインが `plan.md` を再読し、実装順を進捗の管理に展開する。実装担当を 1 体起動し、以下を渡す。

- タスクの目的・受入条件、確定した `plan.md` 全文
- Phase 2 の調査結果と必読ファイル、Phase 4 のレビュー指摘と設計判断の理由
- Phase 2 で取得した規約全文と、適用されるプロジェクト規約
- 作業ディレクトリ、担当するファイル・責務、既存の未コミット変更、必要な検証
- 「同じ作業ツリーには他の作業があるため、他者の変更を戻さず、現在の内容に合わせて実装する」

実装担当が作業している間は、メインも同じ範囲を編集しない。

#### B. 実装と確認

実装担当は確定した計画を実装し、セルフレビューの前に仕様を保つ簡素化と必要な検証を行う。メインは報告と実際の差分を確認し、完了した項目の進捗を更新する。

目的・仕様を左右する不明点、計画と既存実装の不一致があれば、実装担当は変更を広げずメインへ返す。メインが既存の合意で解決できない点だけユーザーに一問ずつ確認し、決定を実装担当へ返す。計画から外れる場合は確認したうえで経緯を `implementation.md` に残す。通常の実装判断は既存規約に従って進める。

実装担当の実装ミスによる検証失敗は 3 回まで自己修正する。それを超える場合はメインへ失敗の根拠と未解決点を返し、メインが「さらに修正試行 / Phase 6 のレビュー対象として差分を渡す / Phase 4 に戻って再策定する」をユーザーに確認する。

#### C. 記録と検証

メインが実装担当の報告を `implementation.md` に保存する。

- 変更ファイルと変更内容、設計上の理由
- 実装中の重要な判断、計画からの変更とその合意
- 実行した検証コマンドと結果、未実施の確認
- 残課題・規約衝突・未解決の論点

必要な検証はプロジェクト規約・CI・変更の影響から決める。UIレビューはこの工程に含まれず、別の工程（linear ではAgent QA）で行う。未実施のUIレビューを完了と報告しない。メインは報告だけで完了とせず、差分と検証の根拠を確認して Phase 6 へ進む。

### Phase 6: 実装後の4役割を並行実行

実装と必要な検証が終わった同じ差分を固定し、次の4役割を並行して起動する。実装後のレビューラウンドは初回を 1 として数え、最大 2 回までとする。計画段階のプランレビューはこの回数に含めない。

起動の前に、実際の変更ファイルの言語・領域・バージョンが Phase 2 で取得した規約の範囲に入るかを確認する。外れる分だけ Phase 2 と同じ条件で補って取得し、全担当へ同じ規約全文を渡す。

| 役割 | 渡す情報 |
|---|---|
| 設計適合性（設計担当1 を再開） | 対象ファイルと差分（staged / unstaged / untracked を含む）、最終計画・受入条件・合意済み変更、実装報告と検証結果、規約全文 |
| 独立コードレビュー（新規） | 同上と、下の「独立コードレビューの前提」 |
| refine（1 体） | 規約全文と関連する `AGENTS.md`・`CLAUDE.md`・docs の該当節、対象ファイル一覧、リポジトリルートの絶対パス、変更範囲の確認コマンド（`git diff HEAD -- <path>`。未追跡ファイルは全行を変更扱い）、バッチID |
| 実装の簡素化（新規） | 目的・受入条件・最終計画・維持する契約・対象ファイルと差分・規約全文 |

独立コードレビューの前提: 計画を正しいと仮定せず、実コード・利用箇所・契約から不具合を確認する。計画と形式的に異なるだけでは不具合にしない。重要度・file:line・影響・根拠・修正案、確認済みと未確認の範囲を返す。設計適合性は設計担当1 の担当なので、ここでは計画との照合ではなくコードの正しさ・安全性・性能・保守性・規約を確認する。

設計担当1 は自身の設計適合性レビューを確定するまで他担当の今回の結果を読まない。先に起動した担当の完了を待ってから次を起動するのではなく、4役割を起動してから結果を待つ。同じ担当を重複起動しない。対象が大きい場合は同じ担当を再開して続きのバッチを渡し、担当数や確認範囲を黙って減らさない。

全担当は読み取り専用で、今回の他担当の結果を読まず、意見を交換しない。メインと実装担当も全結果が揃うまで対象を編集しない。途中で外部の変更が入った場合は、その影響範囲を最新の同じ差分で確認し直してから統合する。

各担当の確認範囲・未完了報告を確認し、未確認部分は同じ担当へ戻す。失敗・未完了を「指摘なし」として処理しない。

初回は `architecture-review.md` / `review.md` / `raw/refine.md` / `raw/simplify.md`、2回目は各ファイル名に `-2` を付けて保存する。4役割の全結果が揃ったら新しい verifier へ渡し、検証結果を `raw/implementation-verification-{round}.md` に保存する。検証完了後、設計担当1 を「指摘統合」として再開し、検証結果全文・原文への参照・差分の更新・検証結果・ラウンド番号を渡す。

### 指摘の検証（Phase 4・6 共通）

全担当の結果が揃ったら、新しい verifier を 1 体起動する。今回のレビューをした担当を流用しない。

- 生レポート全文と原文のパス、各担当の確認範囲、目的・最新計画・受入条件・合意済み変更、対象コードと差分、検証結果、規約全文、ラウンド番号を渡す。
- verifier が各指摘の根拠を検証して出典IDを保持し、重複・誤認・対立・未確認事項を整理する。
- メインは出典の対応と完了状況を確認し、不足を同じ verifier へ戻す。検証不能は未確認として明示し、誤認も削除しない。失敗や未完了を検証済みとして先へ渡さない。

### Phase 7: 設計担当1 が統合し、実装担当が修正

設計担当1 が verifier の報告から全項目の採否を決め、対立・不確実性・設計上の重要点に必要な根拠を確認する。全件の事実確認を最初から繰り返さない。全指摘の採否と理由、採用した修正の対象・責務・具体的な変更・維持する契約・必要な検証を、一つの修正指示として返す。メインはそのまま記録し、仕様・受入条件の変更や未許可の範囲拡大が必要な点だけユーザーに確認する。通常の設計・修正判断をメインでやり直さない。

修正不要なら Phase 9 へ進む。修正があれば、メインが同じ実装担当を再開し、設計担当1 の修正指示・確定した計画・現在の差分・規約・検証条件を渡す。再開できなければ実装履歴と採否を同じ役割の新しい担当へ引き継ぐ。設計担当1 は次のレビューに備えて継続し、コードを編集したり、実装担当を追加で起動したりしない。

実装担当が修正と必要な検証を行い、変更・検証結果・未解決点を返す。メインは設計担当1 の採否と修正結果を `fix-log.md` に記録する。委託不可の場合はメインが同じ観点で対応し、独立した確認とは報告しない。

### Phase 8: 最大2ラウンドで終了する

- **1回目のレビュー後に修正した場合**: 修正後の同じ差分について、Phase 6 の4役割を2回目として並行実行する。最新の計画、前回の指摘と採否、修正内容、検証結果を渡す。全結果を新しい verifier で検証してから設計担当1 に渡し、Phase 7 で必要な最終修正を実施する。
- **2回目のレビュー後に修正した場合**: 実装担当が最終修正と必要なテストを行ったら Phase 9 へ進む。3回目の実装後レビューは起動しない。
- **修正不要の場合**: 回数を埋めるために再実行せず Phase 9 へ進む。

最大2回は実装後の全体レビューに対する上限であり、担当の再開・交代や計画の変更でリセットしない。検証失敗・重大な未解決事項・未完了の担当が残る場合も追加ラウンドで無期限に続けず、その状態を明記してユーザーへ返す。未完了の確認を完了済みのラウンドと偽らない。

### Phase 9: 完了と必要な引き継ぎ

実施したレビュー回数、設計担当1 の判断と修正内容、検証結果、未解決事項を報告する。2回目の後に修正した場合は、その最終差分が再レビューされていないことを明記する。必須検証の失敗や重大な未解決事項があれば作業終了と品質上の完了を区別し、完了済みとは報告しない。

コミットが明示されていれば、その許可範囲と通常／自律モードを `commit` へ引き継ぐ。コミット依頼がなければ未コミットのまま完了し、毎回コミット許可を要求しない。PRやリリースは明示された場合だけ、それぞれ `create-pr`・`release` へ進む。

## 5. 成果物

```text
.shinaps/work/{YYYYMMDD-HHMMSS}-{slug}/
├── plan.md                    ← Phase 4 の全結果を検証・統合した最終 plan
├── raw/
│   ├── explorer.md            ← または explorer-1.md, explorer-2.md ...（引き継ぎ時の補完は explorer-supplement.md）
│   ├── architect-1.md         ← 設計担当1 の独立設計案（2体の設定のみ）
│   ├── architect-2.md         ← 設計担当2 の独立設計案（2体の設定のみ）
│   ├── architect.md           ← 統合した計画（1体の設定では設計担当1 の案）
│   ├── plan-review-{round}-{n}.md   ← 計画レビュー担当 n の結果
│   ├── plan-simplify-{round}-{n}.md ← 計画簡素化担当 n の結果
│   ├── plan-verification-{round}.md ← 計画指摘の検証結果
│   ├── implementation-verification-{round}.md ← 実装指摘の検証結果
│   ├── refine.md              ← Phase 6 の規約照合の生レポート（2 回目は refine-2.md）
│   ├── simplify.md            ← Phase 6 の実装の簡素化の生レポート（2 回目は simplify-2.md）
│   └── architect-revised-{round}.md  ← 計画の修正版（round は 1 始まり）
├── implementation.md          ← 実装ログ・変更ファイル一覧・動作確認結果
├── architecture-review.md     ← 設計担当1 の設計適合性レビュー
├── architecture-review-{n}.md ← 修正後の設計適合性レビュー（n は 2 始まり）
├── review.md                  ← 独立コードレビューの生レポート
├── review-{n}.md              ← 修正後の再レビュー（n は 2 始まり）
└── fix-log.md                 ← 修正ループの履歴（修正があった場合のみ）
```

全担当の応答は全文を参照できる状態で保存する。担当は結果を文字列で返し、進行管理の成果物はメインが保存する。実装担当は担当範囲のコード・テスト・必要なドキュメントだけを編集する。

## 6. 他スキルからの呼び出し

explore・spec・review・debug などは、生成した成果物のパスを入口の引数に直接渡す。専用の引き継ぎファイルは作らない。受け取った成果物は Phase 1・2 のとおりに扱う。どの成果物を渡すかと、既定で使う入口は、元のスキルの引き継ぎの記述に従う。
