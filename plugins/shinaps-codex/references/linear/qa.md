# QAと証拠

Agent QAは、自動テスト・API・ブラウザ・管理画面・Simulatorなど、AIが操作と結果を確認できるもの。Human QAは、人の判断や実機でしか確認できない条件。普通の画面に一律のHuman QAを設けない。不要なら「不要」と記録する。

QAはPRごとに完結させ、複数のPRをまとめるために人の確認を遅らせない。環境ごとに、Agent QAと必要なHuman QAを分ける。Staging QAが必要な公開変更は、本番でも環境差と主要導線を確認する。存在しない環境を合格扱いにしない。

自動検証のコマンドと必須対象は、各プロジェクトの規約・CI・スクリプト（設定の `references.validation`）を正本にする。原因調査の絞り込み実行を、必須検証全体の合格に読み替えない。成否の判定とログの短縮は[テスト方針](../testing.md)に従う。

## 証拠の要件

- 確認日、差分またはコミット、環境、実行内容、期待と実際、未確認事項を含める。
- QAの対象版と実際に動いている版が一致することを、QAの開始前と記録の直前に確認する。マージや配備で版が変わったら、以前の合格を使わず、影響する項目を再確認する。具体的な照合コマンドはプロジェクトの補足に置く。
- Simulator、実機、配備、一般公開を区別する。失敗・取消と、意図せず実行されなかったテストや確認項目を合格にしない。チェックは、対応する性質を確認した証拠がある場合だけ付ける。
- 秘密値・Cookie・個人情報を、設定・Issue・証拠に残さない。

## Simulatorの所有と再利用

Simulator等の仮想端末は、プロジェクトごとのQA専用端末を作成して再利用する。作業ごとの増設や毎回の削除を既定にしない。2ユーザーのE2Eなど複数台が必要な場合は、そのプロジェクトの専用端末として確保する。

- 使う端末をUDIDで固定し、ビルド・インストール・起動・UI操作・終了などの各操作で対象を明示する。起動中の端末や表示中の端末を暗黙に選ばない。
- 端末とプロジェクトの対応、使用状況（端末名・UDID・用途・使用中の作業と開始時刻）は、同じリポジトリの全作業ツリーで1つの記録を共有して調整するため、メインの作業ツリー（[Linear共通設定](configuration.md) の「設定の読み方」）の `.shinaps/work/simulators.md` に記録する。記録の初期化と保全は、メインの作業ツリーを対象に[作業記録](../work-records.md)の手順で行う。他プロジェクトや普段使いの端末を停止・初期化・削除しない。
- 同じプロジェクトの別の作業が使用中なら、調整して順に使い、占有を奪わない。
- 自動QAでは端末を不要に前面へ出さず、人の確認が必要なときに対象を表示する。表示やUI操作ツールの制約で他の作業と衝突する場合は、一方的に切り替えず調整する。

## QAの時点・対象・最終QA

Linear進行でpushまでにCodexへ依頼する動作QAは、次の3つの時点だけにする。push後の環境ごとのAgent QAとCycleの全体QAは、各工程の定めに従う。Claude側の検証・独立レビューとCodexのQAは互いの代わりにしない。

| 時点 | 内容 |
| --- | --- |
| 途中の目的別確認（以下、途中確認） | 開発途中に実現性や実際の動作を確かめる必要があるとき、Claudeが疑問と確認範囲を明示して依頼する。結果はLocal Agent QAの合格に読み替えない |
| Local Agent QA | devの完了後の初回QA。不合格後の再QAも初回QAの一部とし、修正の影響で範囲を決めて合格まで続ける |
| 最終QA | 全コミットの完了後、push前に行う。差分確定中の修正・コミットのたびにはCodexのQAへ戻さず、Claudeが検証・レビューして変更記録を残す |

依頼には、対象リビジョン、変更と影響範囲、既存のQA結果、今回確認したい内容を含める。

- **対象**: 比較元と予定差分を対象とする。対象外の未コミット変更は環境として記録し、対象に含めない。対象外の変更を含む作業ツリーでQAする場合、その影響を比較できなければ全検証にする。対象の識別は `.git` へ書き込まない読み取りで行う。
- **範囲**: 変更の影響と既存結果の有効性で決め、修正量の大小では決めない。影響を特定できる範囲は重点的に確認し、比較できない、または影響を限定できない範囲は全検証する。結果の再利用は[テスト方針](../testing.md)に従う。
- **変更記録**: Local Agent QAの後の各修正・各コミットについて、QAに関わる項目（変更内容・影響範囲・既存QA結果との差分・実施した検証とレビュー・単位案と予定差分の更新）を `fix-log.md` に残したもの。
- **最終QA**: 比較元からのコミット済み差分が、控え（Local Agent QAに合格した時点の比較元と全体差分。[担当と工程](workflow.md)の「単位案からコミット完了まで」で記録する）と一致すれば、根拠を記録して結果を再利用し、一致を確かめたHEADのSHAを最終合格の対象とする。控えは、更新後の全体期待差分（`commit` の照合基準）とは別に扱い、全体期待差分を更新しても書き換えない。一致しなければ、最終的なコミット済み状態を対象にし、変更記録から影響範囲を決めてQAする。比較できなければ全検証にする。Local Agent QAの後に修正サイクルがあれば、報告された体制をLocal Agent QAと同じ基準で照合する。
- **不合格**: devの修正サイクル（[工程](../dev/workflow.md)の「役割と継続」。[UIの微調整](workflow.md#codexによるuiの微調整)の範囲ならCodexの微調整）、必要なレビュー、既存の承認条件でのコミット、影響範囲の再QAを経て、最終状態での合格を確かめる。
- **push**: pushするHEADのSHAが最終合格の対象のSHAと一致することを記録してからpushする。一致しない、または確かめられないならpushしない。

## QAコメントの書式と更新

Codexは各工程のQA結果を、対応するIssueのコメントへ残す。初回と再検証、Local・Staging・Productionを区別する。

```markdown
### <工程・環境> Agent QA — <確認日>
対象: <Issue・比較元・差分またはコミットSHA>
環境: <URL・配備版・端末／ブラウザ・ビルド番号>

| 受入条件 | 確認方法・期待結果 | 実際の結果 | 判定・証拠 |
| --- | --- | --- | --- |
| <条件または要件ID> | <コマンド・操作と期待> | <観測した結果> | <合格／不合格／未確認／対象外と理由、画像・動画・ログへのリンク> |

残項目・次の対応: <誰が何を行うか、再開条件>
再検証の場合: <前回結果へのリンク、修正内容と今回の対象>
```

- 失敗や中断も記録し、成功の結果で過去の失敗を消さない。送信の再試行では重複したコメントを作らない。実際に再検証した場合は、新しい対象と結果を区別して記録する。長いログは必要な箇所を要約して証拠へリンクする。
- 最新の合否と未確認事項は最新のQAコメントで示し、コメント・添付・リンクを読み戻して確認する。
- 人のQAの結果は本人の報告に基づいて対象と結果を記録し、AIが代わりに合格を決めない。

## スクショ・動画

- 画面を変更・検証した場合は、結果を説明できる代表スクショを記録する。遷移・入力・アニメーションなど静止画だけでは判断できない挙動は、操作と結果が分かる短い動画で示す。既存の対象版の素材を再利用できる場合は重複して撮影しない。画面を持たない変更はAPI・ログ等で示し、無関係な画像や動画を求めない。
- 素材には画面名、対象版、環境、端末または画面幅・ブラウザ、確認した内容を添える。レビューで比較が必要な場合は、仕様・デザインや変更前の状態と対応づける。スクショだけで操作の成功を証明せず、期待結果と実際の結果も記録する。
- 保存先は、Linearの添付、設定の `evidence:<保存先>` で許可された先、または利用者がその場で許可した先とする。Issue・QAコメント・Cycle報告から閲覧できるようにし、ローカルの一時パスだけで引き渡しを完了しない。
- 画像の表示、動画の再生、リンク先へのアクセスを確認してから、共有済みとして扱う。埋め込みが使えない場合は説明付きのリンクを使う。保存・撮影ができなければ不足と理由を記録し、取得済みとは扱わない。公開設定を緩めて共有せず、秘密値・Cookie・実利用者の情報を含まない素材を使う。

## Human QAの引き渡し

依頼の前に、対象環境・URLまたはビルド、テストデータ、操作・期待結果・既知の制限をIssueに揃える。対象環境への配備の成功と基本動作を確認してから依頼する。確認の後に対象が変わったら、影響する項目を再確認する。
