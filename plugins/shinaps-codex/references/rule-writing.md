# Shinaps規約の書き方

Shinaps AIへ個人規約を登録・更新するときの書き方。短さそのものではなく、1回読めば判断と行動が分かることを目的にする。

## 1件1判断

1件には1つの判断だけを書く。別々に適用・変更できる判断は分ける。

## 書き込む前に既存の規約と比べる

`record_rule`・`record_rules`・`update_rule` の前に、書き込む全文（scope・labelを含み、更新では更新後の全文）を既存の規約の全文と比べる。比べるのは呼出し元のAIで、類似度の点数は作らない。既存の規約は[Shinaps規約の取得](rules.md)の「書き込む前に取得する」で取得する。全文や範囲が変わったら比べ直す。

比べるのは次の2つ。

- **判断**: 適用条件・求める行動・例外・強さ（強制か推奨か）。文面が違っても全て同じなら同じ判断で、文面が似ていても一つ違えば別の判断とする。適用条件の広さの違いは判断の違いに数えず、範囲で比べる。
- **範囲**: scope・技術のlabel・公式規約の版の条件・適用条件の広さ。

候補ごとに読んだ既存の規約の全てを見て、次の順で最初に当てはまる結果にする。公式規約は読むだけで、書き込み先にしない。

1. **提示**: 同じ場面で既存の規約と両方には従えない、候補に従うと既存の規約の例外や強さが意味を持たなくなる、更新先を一つに決められない、または結果を判断できない。
2. **書かない**: 同じ判断で範囲が候補を含む既存の規約があり、候補に加える情報が無い（言い換えは情報に数えない）。または、同じ判断で範囲が候補を含むのが公式規約だけである（補足があれば報告する）。
3. **提示**: 取得が未完了である。「重複なし」とせず、未取得の範囲を示す。
4. **更新**: 同じ判断で範囲が候補を含む個人規約があり、候補の補足（理由・例・出典）が判断を変えず、その規約の範囲全体に当てはまる。判断・範囲・kindは変えない。
5. **提示**: 同じ判断の個人規約と範囲が重なるが候補を含まない、または補足がその規約の範囲の一部にしか当てはまらない。
6. **新規**: それ以外。別の判断で既存の規約と両立するもの、公式規約より範囲が広い同じ判断を含む。

`update_rule` の依頼では更新対象自身を比較の相手から外し、他の規約で1〜3に当たらなければ結果を更新とする。当たるときは結果を提示とし、更新対象を変えず、更新前の全文のまま残ることを示す。更新対象の削除や他の規約との統合は、利用者が選んだときだけ行う。判断や範囲を変える更新は、更新前後の全文の差分と範囲の変化を示して同意を受ける。

同じ作業で保存前の候補同士は、範囲が広い方（決まらなければ先の候補）を既存の規約とみなして同じ順で比べる。結果が提示なら両方を提示する。更新は相手の候補の下書きへ補足を足すことで、`update_rule` は呼ばず、許可は相手の候補の結果で判断する。書かないと更新は、相手の候補が保存されたときに確定する。相手の全文が変わる、または書かれないときは、書かないまたは更新とした候補を比べ直す。範囲は足し合わせず、呼出しのscopeに揃えるために候補のscopeを変えない。

提示では候補と既存の規約の全文の違い、推奨する結果と理由、その候補を相手とした他の候補を示し、利用者の判断を受ける。提示した全文のまま利用者が選んだ操作は、比べ直さずに書く。同じtitleの既存があるなどで書けなかった候補も提示する。

比較の結果は書き込みの許可にならない。更新・新規は結果が許可された操作・対象と一致するときだけ書き、違えば書かずに提示する。比べた他の規約は変更しない。

結果は候補ごとに、比べた既存の規約のidまたは相手の候補、未確定ならその旨、取得の条件、未完了の範囲と返らない範囲を添えて報告する。

## 機械検査

coding の規約は、使えるlintのルールで検査できるかを判断し、できるものには `checks` を付ける。coverageの決め方・補助の確認・書き込みと、検査を持つ規約の内容を変えるときの見直しは[規約の機械検査](lint.md)の「検査を登録・更新する」に従う。

## 項目の役割

各項目は役割が重ならないようにし、同じ内容を言い換えて繰り返さない。

| 項目 | 書くこと | 書かないこと |
| --- | --- | --- |
| `title` | 判断そのものを一文で | 背景、複数の判断 |
| `why` | その判断をする理由と、守らないと起きること | 手順、`recommend` の言い換え |
| `recommend` | 読み手がそのまま取れる具体的な行動 | 理由、一般論 |
| `avoid` | 誤りやすい行動 | `recommend` の単なる否定 |
| `examples` | good と bad の違いが分かる最小のコード片 | 違いに関係しない行、架空の根拠 |

## 残すものと削るもの

- 適用条件、例外、強制か推奨かの強さは必ず残す。短くするために意味を変えない。
- 経緯、PR番号、発生日は、判断の根拠や適用範囲を理解するために必要な分だけ残す。詳細な出典は `sourceUrls` に置く。
- 出典、scope、kind、labelsは、規約の内容が変わらない限り変えない。出典を足すときは既存の出典を残す。
- 読み手がリポジトリの既存の規約や公式の文書から分かることは繰り返さない。
- 根拠の無いコード例・URL・規範を作らない。

## scope

全リポジトリに当てはまる判断だけ `scope: user` にして、他のプロジェクトでも通じる表現で書く。同じownerの配下に共通する判断は `scope: repo_owner`、特定のリポジトリの判断は `scope: repo` にして具体的に書く。`scope: repo` で書くには、[Shinaps規約の取得](rules.md)の「リポジトリを特定する」でrepositoryの `id` を得る。

## 目安と上限

目安は書き方の基準で、超えても保存できる。超えるときは、1件に複数の判断が入っていないか、項目の間で繰り返していないかを見直す。必要な適用条件と例外を落としてまで目安に合わせない。

| 項目 | 目安 |
| --- | --- |
| `title` | 60字 |
| `why` | 300字 |
| `recommend` | 250字 |
| `avoid` | 150字 |
| `examples` の good・bad | 各300字、15行 |

上限はサーバーが入力を拒否する値で、目標ではない。値はMCPツールの入力の説明に従う。超過はエラーになり保存されないので、切り詰めずに書き直す。record_rulesは1件でも超えると全体が保存されない。
