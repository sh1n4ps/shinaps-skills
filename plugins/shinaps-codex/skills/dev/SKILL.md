# 開発

1. 対象のAGENTS.md、既存構造、CIと関連する仕様・調査記録を読む。追加より設計変更が適切でないか検討し、受入条件を性質としてまとめる。仕様を変える判断だけ確認する。
2. Shinaps AIのルール検索が利用できれば、リポジトリと変更領域に関係するルールを取得する。使えない場合はルール照合未確認として明記し、可能な実装を進める。
3. 複雑な調査・設計では、委託を許可されている場合に登録済みのshinaps-explorer、shinaps-architect、shinaps-plan-reviewerへ対象と期待する結果を渡す。担当の結論を自分で検証する。委託不可なら同じ観点を現在のセッションで確認する。worktree作成は別途許可が必要。
4. 計画を必要な単位に分けて実装する。利用できる計画ツールで進捗を管理する。既存の無関係な変更を保ち、公開契約を変える必要が出たら理由と案を確認する。
5. $shinaps:simplifyを読み、仕様を保つ削除・統合を行う。CIや既存スクリプトから変更に必要な検証を実行する。UIが関係する場合は$shinaps:verify-uiを使い、対象プロジェクトで必要な実画面を確認する。
6. $shinaps:refineによるルール照合が可能なら行い、$shinaps:reviewで最終差分をレビューする。確定した今回の不具合を修正し、影響範囲を再検証する。依頼外の既存問題は混ぜず報告する。
7. 変更後の挙動、主要な検証と未確認事項を報告する。コミット・PR・公開は別途依頼された場合だけ進める。

受け取った仕様書や調査記録は、現在の依頼との整合性を確認して引き継ぐ。ツールやスキルが未提供なら存在を仮定せず、その制約を示す。質問には現在利用できる入力ツールを使い、一問ずつ回答を待つ。

記録は必要な場合に.shinaps/work/へ保存する。.shinaps/.gitignoreは未作成なら`*`と改行で作成し、既存の場合は内容を保持して必要な除外だけ追加する。追跡済みファイルや既存記録は削除しない。
