# shinaps:commit — レビュー単位分割コミットモード

このスキルは「実装が一通り終わった working tree の差分」を入力に、**人間がレビューできる小さい単位** へ分割し、単位ごとにレビュー + フィードバックループを回しながら段階的にコミットするための手順書。

大きい差分を 1 コミットで積むと人間のレビューが形骸化する。逆に、単位ごとに「diff 提示 → 人間 OK / 修正指示 → 修正 → コミット」の小さいループを回せば、レビューの認知負荷が下がり、修正も差分が小さいうちに済む。さらに各単位を **その単位だけ適用した状態で検証** してからコミットすることで、`git bisect` や revert が安全に使える「どこに checkout しても壊れていない履歴」を保証する。

shinaps-ai MCP server は必須ではない (git とローカル検証だけで完結する)。登録済みなら分割判断や修正判断で `record_memory` を残す。

## 引数仕様

| 呼び出し | 動作 |
|---|---|
| `/shinaps:commit` | working tree の全差分 (staged + unstaged + untracked) を対象に自動分割 |
| `/shinaps:commit <補足>` | 補足を分割方針のヒントとして扱う (例: 「スキーマ変更を先に」「テストは実装と同じコミットに」) |
| `Skill(skill="shinaps:commit", args="...")` | `/shinaps:dev` 等からの handoff。implementation.md のパスが含まれていれば Read して分割の参考にする |

**スコープ外**: push 済みコミットの再分割 (`git reset` を伴う履歴書き換え) は扱わない。対象は常に「まだコミットされていない差分」のみ。

## Step 0. 前提チェック (MUST)

1. `git status` を確認。以下の場合は **中断してユーザーに報告**:
   - merge / rebase / cherry-pick が進行中 (`.git/MERGE_HEAD` 等がある状態)
   - 差分が 0 件 (staged + unstaged + untracked すべて空)
2. `git stash list` の件数を記録する (このスキルが積んだ stash と既存 stash を混同しないため)
3. 既にステージ済みの差分がある場合は「既存のステージ内容も分割対象に含めて仕切り直す」ことを 1 行で宣言する (Step 2 の単位ステージングは毎回 `git reset` から始まるため、ユーザーが手動で作った index は保持されない)
4. 検証コマンドを確定する: リポジトリの package.json scripts / CLAUDE.md / 直近の CI 設定から 型チェック / lint / test のコマンドを特定する。特定できない場合は `AskUserQuestion` で確認する

## Step 1. 差分分析と分割計画

1. `git diff HEAD` + `git status --porcelain` (untracked 含む) で差分全体を把握する。handoff 時に implementation.md があれば Read し、変更の WHY と依存関係を取り込む
2. 差分を **レビュー単位** に分割する。分割の原則:
   - **1 単位 = コミットメッセージ一言で「何をやったか」を説明しきれる範囲**。迷ったら小さく切る。例えば API 実装なら「スキーマ追加」「リポジトリ実装」「コントローラ実装」「ハンドラ実装」をそれぞれ別コミットにするくらいの粒度が基本
   - **まとめた方が人間がレビューしやすいと判断した場合は、複数レイヤーを 1 単位に統合してよい** (例: 数行しかない配線変更を実装本体と同居させる)。ただし統合後も一言で説明できる範囲を超えないこと (目安: 差分 150 行以内。超える場合も「意味的に不可分」なら許容し、計画にその旨を書く)
   - 「ファイルの種類」ではなく「レビュー時に一緒に読みたいか」で切る
   - **依存順に並べる**: 後の単位が前の単位に依存するのは OK、逆は NG (各コミット時点で参照先が存在しない状態を作らない)
   - **テストはテスト対象の実装と同じ単位に入れることを優先** する (その単位単独で test が通ることが検証で保証できるため)。テストだけ別単位に分けるのは、テスト自体がレビューの主題になる場合のみ
   - **ファイル単位の分割を基本** とし、1 ファイルが複数単位にまたがる hunk 分割は本当に必要なときだけ使う (Step 2 のステージングと検証が複雑になるため)
3. 分割計画を提示する: 単位ごとに「対象ファイル / 概要 / 想定コミットメッセージ / 依存関係」を表で示し、`AskUserQuestion` で確認する:
   - **この分割で進める**
   - **分割を調整する** (ユーザーの指示で計画を修正して再提示)
   - **中止する**

## Step 2. 単位ごとのレビューループ

確定した計画の順に、単位ごとに以下を繰り返す。

### 2-a. ステージング

1. `git reset` で index をクリアする (前の単位の残留や手動ステージを排除し、毎回クリーンな状態から積む)
2. その単位のファイルを `git add <file>...` でステージする。untracked の新規ファイルも同様
3. hunk 分割が必要なファイルのみ: `git diff HEAD -- <file>` の出力を scratchpad にパッチとして保存し、対象単位に属さない hunk を削除してから `git apply --cached <patch>` でステージする (対話型の `git add -p` はこの環境では使えない)
4. `git diff --cached --stat` で計画どおりの内容がステージされたことを確認する

### 2-b. 単独検証

「この単位 + コミット済みの単位だけが適用された状態」を作って検証する:

1. `git stash push --keep-index --include-untracked -m "shinaps:commit unit-{n} verify"` — 未ステージ分 (残りの単位) を退避する。**直後に `git rev-parse stash@{0}` で stash の SHA を記録する** (万一 drop しても `git stash apply <SHA>` で復元できる保険)
2. 型チェック / lint / test を Step 0 で確定したコマンドで実行する
3. **コミットする前に** `git stash pop` で退避分を戻す (index はステージ内容を保持したまま残る)。コミット後に pop すると stash に含まれるステージ済み hunk の再適用でコンフリクトしやすいため、pop は必ずコミット前に行う
4. pop がコンフリクトした場合は自動で解決しようとせず、コンフリクト内容と記録済み stash SHA を提示して `AskUserQuestion` で対応を確認する (stash は drop されずに残っているので作業は失われていない)
5. 検証が失敗した場合:
   - 原因がこの単位内 → 修正して 2-a からやり直す
   - 原因が「後の単位に依存している」(この単位単独では参照先が無い等) → 分割の依存順が誤っている。Step 1 に戻って計画を組み替えるか、依存先の単位と統合する。**検証をスキップして進めるのは禁止** (壊れたコミットを履歴に残さない、というこのスキルの存在理由に反する)

### 2-c. 人間レビュー

1. `git diff --cached` の内容を要約して提示する: 変更の概要 / なぜこの変更か (implementation.md 由来の WHY があれば添える) / 検証結果 / 提案コミットメッセージ
2. `AskUserQuestion` で確認する:
   - **このままコミット** — 提案メッセージでコミットする
   - **修正が必要** — ユーザーの指摘を受けて 2-d の修正ループへ
   - **この単位をスキップ** — index を `git reset` で戻し、単位を未処理のまま次へ (最後にまとめて報告)
   - **分割をやり直す** — 残りの単位を対象に Step 1 に戻る

### 2-d. 修正ループ (修正指示があった場合)

1. 指摘内容を Edit / Write で修正する
2. **2-a のステージングからやり直す** (修正で差分が変わっているため)
3. 2-b の単独検証 → 2-c の提示を再度行う。人間が OK するまでこのループを回す
4. 修正内容が他の単位 (コミット済み含む) に波及する場合はその場で報告する。コミット済み単位への波及は履歴を書き換えず、**波及修正を独立した後続単位として計画に追加** する

### 2-e. コミット

1. コミットメッセージは `git log --oneline -10` で確認した **リポジトリの既存規約** に合わせる (例: `fix(api): ...` 形式のセマンティックメッセージ)
2. `git commit -m "..."` を単独で実行する (`git add` と `git commit` を `&&` で連結しない)。**Claude-Session トレイラは付けない**
3. 単位の完了を 1 行で報告し、次の単位へ進む

## Step 3. 完了報告

全単位の処理後:

1. `git log --oneline` で積んだコミット一覧を提示する
2. スキップした単位・working tree に残った差分があれば明示する (「全部コミットした」と誤認させない)
3. `git stash list` を Step 0 の記録と突き合わせ、このスキルが積んだ stash が残っていないことを確認する
4. shinaps-ai MCP が使えるなら、分割方針や修正ループでの判断を `record_memory` に残す
5. push / PR 作成はこのスキルでは行わず、必要なら create-pr skill 等へ案内する

## 動作原則

- **壊れたコミットを積まない**: 単独検証を通過していない単位はコミットしない。検証スキップの誘惑に負けない
- **人間の OK なしにコミットしない**: 2-c の確認は単位ごとに必ず行う。まとめて事後承認にしない
- **stash を消失させない**: push 直後に SHA を記録し、pop 失敗時は自動リカバリせずユーザーに委ねる
- **git 操作は 1 コマンドずつ**: add / commit / reset / stash を `&&` で連結しない
- **履歴は書き換えない**: コミット済み単位への修正は amend / rebase ではなく後続コミットで積む
- **報告は正確に**: スキップ・残差分・検証失敗は隠さず報告する

## 他スキルからの呼び出し

`/shinaps:dev` の完了後 (Phase 8 まで終了し、ユーザーが実装内容を了承した後) に handoff される想定:

```
Skill(skill="shinaps:commit", args="<タスク要約>。実装の WHY は .claude/shinaps/{ts}-{slug}/implementation.md を参照")
```

implementation.md が渡された場合は Step 1 の分割判断と 2-c の WHY 提示に活用する。
