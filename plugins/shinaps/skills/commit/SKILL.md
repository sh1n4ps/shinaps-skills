# shinaps:commit — レビュー単位分割コミットモード

実装が一通り終わった working tree の差分を、人間がレビューできる小さい単位に分割し、単位ごとに「diff 提示 → 人間 OK / 修正指示 → 修正 → コミット」のループを回しながら段階的にコミットする。各単位は **その単位だけ適用した状態で検証** してからコミットし、`git bisect` / revert が安全に使える「どこに checkout しても壊れていない履歴」を作る。

方式は **サイクル型 stash**: 単位ごとに「その単位以外を stash へ退避 → 検証 + レビュー + コミット → stash を全部 pop で戻す」を繰り返す。退避を使い回さず毎サイクル戻すのは意図的な判断で、(1) レビュー中の worktree が「コミット済み + いまの単位」だけになり検証もそのまま実行できる、(2) レビュー修正と退避中の残差分の食い違いが pop 時のコンフリクトとして毎回表面化・解消され、ドリフトが蓄積しない、(3) pop 直後は残差分が常に整合した状態なので次の単位の切り方をそこで見直せる、ため。手数の多さより正確さを優先している。

shinaps-ai MCP server は必須ではない。登録済みなら分割判断や修正判断で `record_memory` を残す。

## 引数仕様

| 呼び出し | 動作 |
|---|---|
| `/shinaps:commit` | working tree の全差分 (staged + unstaged + untracked) を対象に自動分割 |
| `/shinaps:commit <補足>` | 補足を分割方針のヒントとして扱う (例: 「スキーマ変更を先に」) |
| `Skill(skill="shinaps:commit", args="...")` | `/shinaps:dev` 等からの handoff。implementation.md のパスがあれば Read して分割の参考にする |

**スコープ外**: push 済みコミットの再分割 (履歴書き換え)。対象は常に「まだコミットされていない差分」のみ。

## Step 0. 前提チェック (MUST)

1. `git status` を確認。merge / rebase / cherry-pick 進行中、または差分 0 件なら **中断してユーザーに報告**
2. `git stash list` の件数を記録する (このスキルが積む stash と既存 stash を混同しないため)
3. ステージ済み差分があれば「既存の index も分割対象に含めて仕切り直す」ことを 1 行で宣言する (サイクル内で index は毎回作り直されるため保持されない。staged 版と worktree 版が食い違うファイルは worktree 版を採用)
4. 検証コマンド (型チェック / lint / test) を package.json scripts / CLAUDE.md / CI 設定から特定する。特定できなければ `AskUserQuestion` で確認

## Step 1. 差分分析と分割計画

1. `git diff HEAD` + `git status --porcelain` (untracked 含む) で差分全体を把握する。handoff 時に implementation.md があれば Read し、変更の WHY と依存関係を取り込む
2. 差分を **レビュー単位** に分割する:
   - **1 単位 = コミットメッセージ一言で「何をやったか」を説明しきれる範囲**。迷ったら小さく切る (例: API 実装なら「スキーマ追加」「リポジトリ実装」「コントローラ実装」「ハンドラ実装」を別コミットにする粒度)
   - **下限: その単位の diff だけを読んで、変更の妥当性を人間が判断できること** (新しい関数ならその使われ方、シグネチャ変更なら呼び出し元の追従、実装ならその期待挙動を示すテスト)。満たせない場合の対処は優先順に: **① 分割の組み替え** (単位の切り直しで判断できる範囲を作る) → **② それでも無理なら判断材料のファイルを単位に追加**。安易な統合で単位を太らせない
   - 統合後も一言で説明できる範囲を超えないこと (目安: 差分 150 行以内。超える場合は「意味的に不可分」なら許容し、計画にその旨を書く)
   - **依存順に並べる**: 後の単位が前の単位に依存するのは OK、逆は NG
   - **テストはテスト対象の実装と同じ単位に入れることを優先** (単位単独で test が通ることを検証で保証できる)
   - **ファイル単位の分割を基本** とし、1 ファイルが複数単位にまたがる hunk 分割は本当に必要なときだけ使う
3. 単位ごとに「対象ファイル / 概要 / 想定コミットメッセージ / 依存関係」を表で提示し、`AskUserQuestion` で確認する: **この分割で進める / 分割を調整する / 中止する**

## Step 2. 単位ごとのサイクル

計画の順に 2-a 〜 2-f を繰り返す。サイクル開始時点の worktree には常に「残りの全差分」がある (初回は元の全差分、以後は直前の 2-f で pop 済みの状態)。

### 2-a. 退避: 次の単位「以外」を stash へ

1. `git status --porcelain` から **この単位に属さないファイル** を列挙し、`git stash push --include-untracked -m "shinaps:commit backlog {n}" -- <ファイル>...` で退避する
2. **直後に `git rev-parse stash@{0}` で stash の SHA を記録する** (`stash@{0}` は位置がずれるし、万一 drop しても gc 前なら `git stash apply <SHA>` で復元できる保険)
3. **hunk 分割ファイルのみ**: stash に入れず worktree に残し、`git diff HEAD -- <file>` を scratchpad にパッチ保存 → 単位外 hunk だけのパッチを `git apply -R` で一時的に外す → 2-f の pop 後に `git apply` で戻す。パッチは戻し終わるまで削除しない
4. `git status` で「この単位のファイルだけが変更状態」になったことを確認する

### 2-b. 単独検証

worktree がそのまま「この単位 + コミット済みの単位」なので、Step 0 の検証コマンドを直接実行する。失敗した場合:

- 原因がこの単位内 → 修正して再検証
- 原因が後の単位への依存 (参照先が無い等) → 依存順の誤り。`git stash pop` で戻して Step 1 から計画を組み替える
- **検証をスキップして進めるのは禁止** (壊れたコミットを積まない、というこのスキルの存在理由に反する)

### 2-c. 人間レビュー

1. この単位のファイルを `git add <file>...` でステージし、`git diff --cached` を要約して提示する: 変更の概要 / WHY (implementation.md 由来があれば添える) / 検証結果 / 提案コミットメッセージ。diff の外に妥当性の判断材料があるなら 1-2 行で補足し、補足で足りないほど文脈が外にあるなら Step 1 の下限原則 (組み替え優先) で分割を見直す
2. `AskUserQuestion` で確認する:
   - **このままコミット**
   - **修正が必要** → 2-d へ
   - **この単位をスキップ** — `git reset` で index を戻し、コミットせず worktree に残したまま 2-f へ (最後にまとめて報告)
   - **分割をやり直す** — `git stash pop` で全部戻し、残りを対象に Step 1 へ

### 2-d. 修正ループ

1. 指摘を Edit / Write で修正する。**stash 退避中のファイルへ波及する修正でも構わない** — 食い違いは 2-f の pop 時にコンフリクトとして表面化し、その場で解消する
2. 2-b の検証 → 2-c の提示を、人間が OK するまで繰り返す
3. コミット済み単位への波及は履歴を書き換えず、**独立した後続単位として計画に追加** する

### 2-e. コミット

1. メッセージは `git log --oneline -10` で確認した **リポジトリの既存規約** に合わせる
2. `git commit -m "..."` を単独で実行する (`git add` と `&&` で連結しない)。**Claude-Session トレイラは付けない**

### 2-f. 全戻し: pop してコンフリクトをその場で解消

1. `git stash pop` で退避分を全部戻す
2. **コンフリクトはその場で毎回解消する** (conflict marker を持ち越さない)。コンフリクト時は git が stash を自動 drop しないので、解消と確認を終えてから `git stash drop` する (2-a の SHA と突き合わせる)
3. `git apply -R` していたパッチがあれば `git apply` で戻す
4. `git status` + `git diff HEAD --stat` で残差分を確認し、解消したコンフリクトは 1 行で報告する。修正の波及等で残差分が計画とずれていたら、次のサイクルへ進む前に残りの分割を見直す

## Step 3. 完了報告

1. `git log --oneline` で積んだコミット一覧を提示する
2. `git status` でスキップ分など未コミット残があれば明示する (「全部コミットした」と誤認させない)
3. `git stash list` を Step 0 の記録と突き合わせ、このスキルの stash が残っていないことを確認する
4. shinaps-ai MCP が使えるなら分割・修正の判断を `record_memory` に残す
5. push / PR はこのスキルでは行わず、必要なら create-pr skill 等へ案内する

## 動作原則

- **壊れたコミットを積まない**: 単独検証を通過していない単位はコミットしない
- **人間の OK なしにコミットしない**: 単位ごとに必ず 2-c の確認を挟む
- **pop のコンフリクトは毎サイクルその場で解消**: 残差分を常にコミット済み内容と整合させる
- **stash を消失させない**: push 直後に SHA を記録し、pop コンフリクト時は解消確認まで drop しない
- **git 操作は 1 コマンドずつ**: add / commit / stash 等を `&&` で連結しない
- **履歴は書き換えない**: コミット済みへの修正は amend / rebase ではなく後続コミットで積む
- **報告は正確に**: スキップ・未コミット残・検証失敗・コンフリクト解消箇所は隠さない

## 他スキルからの呼び出し

`/shinaps:dev` 完了後 (ユーザーが実装内容を了承した後) の handoff:

```
Skill(skill="shinaps:commit", args="<タスク要約>。実装の WHY は .claude/shinaps/{ts}-{slug}/implementation.md を参照")
```

implementation.md は Step 1 の分割判断と 2-c の WHY 提示に使う。
