# shinaps:commit — レビュー単位分割コミットモード

このスキルは「実装が一通り終わった working tree の差分」を入力に、**人間がレビューできる小さい単位** へ分割し、単位ごとにレビュー + フィードバックループを回しながら段階的にコミットするための手順書。

大きい差分を 1 コミットで積むと人間のレビューが形骸化する。逆に、単位ごとに「diff 提示 → 人間 OK / 修正指示 → 修正 → コミット」の小さいループを回せば、レビューの認知負荷が下がり、修正も差分が小さいうちに済む。さらに各単位を **その単位だけ適用した状態で検証** してからコミットすることで、`git bisect` や revert が安全に使える「どこに checkout しても壊れていない履歴」を保証する。

方式は **サイクル型 stash 方式**: 単位ごとに「その単位**以外**を stash へ退避 → 検証 + レビュー + コミット → stash を**全部 pop で戻す**」を繰り返す。1 回の退避を使い回さず、毎サイクル戻して退避し直すのは意図的な設計判断:

- **レビュー中の視界が単位に一致する**: worktree には「コミット済み + いまの単位」しかないので、検証は worktree をそのまま実行すればよく、`git status` / `git diff` にもレビュー対象しか映らない
- **pop のたびに残差分が最新状態へリセットされる**: レビュー指摘で入れた修正やコミット済み内容と、stash に退避していた残差分の食い違いは、pop 時のコンフリクトとして**毎回その場で表面化して解消する**。差分のドリフトが蓄積しないので、人間は各コミットのスコープに対して自由に修正指示を出せる
- **分割計画をサイクルごとに見直せる**: pop 直後の worktree は常に「残りの全差分が整合した状態」なので、次の単位の切り方をその時点の実態に合わせて再判断できる

手数は多いが、正確さ (壊れていない履歴 + ドリフトしない残差分) を優先してこのフローを採る。

shinaps-ai MCP server は必須ではない (git とローカル検証だけで完結する)。登録済みなら分割判断や修正判断で `record_memory` を残す。

## 引数仕様

| 呼び出し | 動作 |
|---|---|
| `/shinaps:commit` | working tree の全差分 (staged + unstaged + untracked) を対象に自動分割 |
| `/shinaps:commit <補足>` | 補足を分割方針のヒントとして扱う (例: 「スキーマ変更を先に」「テストは実装と同じコミットに」) |
| `Skill(skill="shinaps:commit", args="...")` | `/shinaps:dev` 等からの handoff。implementation.md のパスが含まれていれば Read して分割の参考にする |

**スコープ外**: push 済みコミットの再分割 (`git reset` を伴う履歴書き換え) は扱わない。対象は常に「まだコミットされていない差分」のみ。

## Step 0. 前提チェック (MUST)

1. `git status` を確認。以下の場合は **中断してユーザーに報告**:
   - merge / rebase / cherry-pick が進行中 (`.git/MERGE_HEAD` 等がある状態)
   - 差分が 0 件 (staged + unstaged + untracked すべて空)
2. `git stash list` の件数を記録する (このスキルが積む stash と既存 stash を混同しないため)
3. 既にステージ済みの差分がある場合は「既存のステージ内容も分割対象に含めて仕切り直す」ことを 1 行で宣言する (サイクル内の退避と再ステージで index は毎回作り直されるため、ユーザーが手動で作った index は保持されない。staged 版と worktree 版が食い違うファイルは worktree 版を採用する)
4. 検証コマンドを確定する: リポジトリの package.json scripts / CLAUDE.md / 直近の CI 設定から 型チェック / lint / test のコマンドを特定する。特定できない場合は `AskUserQuestion` で確認する

## Step 1. 差分分析と分割計画

1. `git diff HEAD` + `git status --porcelain` (untracked 含む) で差分全体を把握する。handoff 時に implementation.md があれば Read し、変更の WHY と依存関係を取り込む
2. 差分を **レビュー単位** に分割する。分割の原則:
   - **1 単位 = コミットメッセージ一言で「何をやったか」を説明しきれる範囲**。迷ったら小さく切る。例えば API 実装なら「スキーマ追加」「リポジトリ実装」「コントローラ実装」「ハンドラ実装」をそれぞれ別コミットにするくらいの粒度が基本
   - **ただし小ささには下限がある: その単位の diff だけを読んで、変更内容の妥当性 (正しさ・意図) を人間が判断できるスコープを保つこと**。妥当性の判断材料 (新しい関数ならその使われ方、シグネチャ変更なら呼び出し元の追従、実装ならその期待挙動を示すテスト) が別単位に散っていて「これ単体では正しいのか判断しようがない」状態になるなら、小さすぎる。判断に必要な相手側を同じ単位に統合する
   - **まとめた方が人間がレビューしやすいと判断した場合は、複数レイヤーを 1 単位に統合してよい** (例: 数行しかない配線変更を実装本体と同居させる)。ただし統合後も一言で説明できる範囲を超えないこと (目安: 差分 150 行以内。超える場合も「意味的に不可分」なら許容し、計画にその旨を書く)
   - 「ファイルの種類」ではなく「レビュー時に一緒に読みたいか」で切る
   - **依存順に並べる**: 後の単位が前の単位に依存するのは OK、逆は NG (各コミット時点で参照先が存在しない状態を作らない)
   - **テストはテスト対象の実装と同じ単位に入れることを優先** する (その単位単独で test が通ることが検証で保証できるため)。テストだけ別単位に分けるのは、テスト自体がレビューの主題になる場合のみ
   - **ファイル単位の分割を基本** とし、1 ファイルが複数単位にまたがる hunk 分割は本当に必要なときだけ使う (Step 2-a の退避がパッチ編集を伴う手作業になるため)
3. 分割計画を提示する: 単位ごとに「対象ファイル / 概要 / 想定コミットメッセージ / 依存関係」を表で示し、`AskUserQuestion` で確認する:
   - **この分割で進める**
   - **分割を調整する** (ユーザーの指示で計画を修正して再提示)
   - **中止する**

## Step 2. 単位ごとのサイクル

計画の順に、単位ごとに 2-a 〜 2-f の 1 サイクルを回す。サイクルの開始時点で worktree には常に「残りの全差分」がある (初回は元の全差分、2 回目以降は直前サイクルの 2-f で pop 済みの状態)。

### 2-a. 退避: 次の単位「以外」を stash へ

1. 現在の worktree の変更ファイル一覧 (`git status --porcelain`) から、**この単位に属さないファイル** を列挙する
2. `git stash push --include-untracked -m "shinaps:commit backlog {n}" -- <この単位以外のファイル>...` で退避する (pathspec 付き stash)。**直後に `git rev-parse stash@{0}` で stash の commit SHA を記録する** (`stash@{0}` は他の stash 操作で位置がずれるし、SHA を控えておけば万一 drop しても gc 前なら `git stash apply <SHA>` で復元できる保険)
3. **hunk 分割が必要なファイルのみ** (この単位と後続単位が同一ファイルの別 hunk を持つ場合): そのファイルは stash に入れず worktree に残し、`git diff HEAD -- <file>` を scratchpad にパッチ保存 → この単位に属さない hunk だけのパッチを作り `git apply -R` で worktree から一時的に外す → 2-f の pop 後に `git apply` で戻す。パッチファイルは戻し終わるまで削除しない
4. `git status` で「この単位のファイルだけが変更状態」になったことを確認する

### 2-b. 単独検証

worktree がそのまま「この単位 + コミット済みの単位」の状態なので、stash の出し入れなしで Step 0 で確定した型チェック / lint / test を直接実行する。

検証が失敗した場合:

- 原因がこの単位内 → 修正して再検証
- 原因が「後の単位に依存している」(この単位単独では参照先が無い等) → 分割の依存順が誤っている。`git stash pop` で一度全部戻し、Step 1 に戻って計画を組み替える (依存先との統合を含む)。**検証をスキップして進めるのは禁止** (壊れたコミットを履歴に残さない、というこのスキルの存在理由に反する)

### 2-c. 人間レビュー

1. この単位のファイルを `git add <file>...` でステージし、`git diff --cached` の内容を要約して提示する: 変更の概要 / なぜこの変更か (implementation.md 由来の WHY があれば添える) / 検証結果 / 提案コミットメッセージ。提示前に「この diff だけで人間が妥当性を判断できるか」を自問し、diff の外にある判断材料 (この変更が後続単位でどう使われるか等) が要るなら要約に 1-2 行で補足する。補足で足りないほど文脈が外にあるなら、それは分割が細かすぎるサイン — Step 1 の下限原則に従い単位を統合し直す
2. `AskUserQuestion` で確認する:
   - **このままコミット** — 提案メッセージでコミットする
   - **修正が必要** — ユーザーの指摘を受けて 2-d の修正ループへ
   - **この単位をスキップ** — `git reset` で index を戻したうえで、この単位もコミットせず worktree に残したまま 2-f の pop へ進む (未コミットとして最後にまとめて報告)
   - **分割をやり直す** — `git stash pop` で全部戻し、残りの単位を対象に Step 1 に戻る

### 2-d. 修正ループ (修正指示があった場合)

1. 指摘内容を Edit / Write で修正する。修正はこの単位のスコープに閉じるのが基本だが、**stash に退避中のファイルへ波及する内容でも構わない** — 食い違いは 2-f の pop 時にコンフリクトとして表面化し、その場で解消する (毎サイクル pop で戻すのはこのため)
2. 2-b の単独検証 → 2-c の提示を再度行う。人間が OK するまでこのループを回す
3. コミット済み単位への波及は履歴を書き換えず、**波及修正を独立した後続単位として計画に追加** する

### 2-e. コミット

1. コミットメッセージは `git log --oneline -10` で確認した **リポジトリの既存規約** に合わせる (例: `fix(api): ...` 形式のセマンティックメッセージ)
2. `git commit -m "..."` を単独で実行する (`git add` と `git commit` を `&&` で連結しない)。**Claude-Session トレイラは付けない**

### 2-f. 全戻し: stash を pop してコンフリクトをその場で解消

1. `git stash pop` で退避分を全部 worktree に戻す
2. **コンフリクトが出たら、その場で毎回解消する** (conflict marker を残したまま次のサイクルへ進まない)。コンフリクト時は git が stash エントリを自動 drop しないので、解消を終えて内容を確認してから `git stash drop` する (2-a で記録した SHA とエントリを突き合わせる)
3. hunk 分割で `git apply -R` していたパッチがあれば `git apply` で戻す
4. `git status` + `git diff HEAD --stat` で「残りの差分が期待どおり揃っている」ことを確認し、解消したコンフリクトがあれば 1 行で報告する
5. 残差分の実態が計画とずれた場合 (コンフリクト解消や修正の波及で単位の中身が変わった等) は、残りの単位の分割をここで見直してから次のサイクルへ進む

## Step 3. 完了報告

全単位の処理後 (最後のサイクルの 2-f まで完了した状態):

1. `git log --oneline` で積んだコミット一覧を提示する
2. `git status` を確認し、スキップした単位など worktree に残った未コミット差分があれば明示する (「全部コミットした」と誤認させない)
3. `git stash list` を Step 0 の記録と突き合わせ、このスキルが積んだ stash が残っていないことを確認する
4. shinaps-ai MCP が使えるなら、分割方針や修正ループでの判断を `record_memory` に残す
5. push / PR 作成はこのスキルでは行わず、必要なら create-pr skill 等へ案内する

## 動作原則

- **壊れたコミットを積まない**: 単独検証を通過していない単位はコミットしない。検証スキップの誘惑に負けない
- **人間の OK なしにコミットしない**: 2-c の確認は単位ごとに必ず行う。まとめて事後承認にしない
- **pop のコンフリクトは毎サイクルその場で解消する**: conflict marker を持ち越さない。残差分を常にコミット済み内容と整合した状態に保つ
- **stash を消失させない**: push 直後に SHA を記録する。pop がコンフリクトした場合、解消と確認を終えるまで stash エントリを drop しない
- **git 操作は 1 コマンドずつ**: add / commit / reset / stash / checkout を `&&` で連結しない
- **履歴は書き換えない**: コミット済み単位への修正は amend / rebase ではなく後続コミットで積む
- **報告は正確に**: スキップ・未コミット残・検証失敗・コンフリクト解消箇所は隠さず報告する

## 他スキルからの呼び出し

`/shinaps:dev` の完了後 (Phase 8 まで終了し、ユーザーが実装内容を了承した後) に handoff される想定:

```
Skill(skill="shinaps:commit", args="<タスク要約>。実装の WHY は .claude/shinaps/{ts}-{slug}/implementation.md を参照")
```

implementation.md が渡された場合は Step 1 の分割判断と 2-c の WHY 提示に活用する。
